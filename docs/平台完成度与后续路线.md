# 通用 Agent 平台完成度与后续路线

## 当前结论

截至 2026-09-10，平台已达到“企业级功能闭环、生产前验证阶段”。双服务边界、通用执行主链、统一 Runtime Protocol、Simulation Replay、插件化内核、Capability Policy、双执行模式及 TypeScript/Java SDK 均已完成当前范围；尚不能仅凭本地 E2E 宣称“大规模生产成熟”，剩余工作集中在真实集群、供应链安全和商业运营。

## 已完成能力

1. Agent 会话、通用状态、模型级上下文预算、自动压缩、长期记忆与多轮连续性
2. LLM Decision、Planner、自动 Replan、Workflow 公共执行契约、审批恢复和多 Agent Delegation
3. 内置 Tool SPI、外部 HTTP、MCP Streamable HTTP/stdio/legacy SSE、生命周期、熔断、故障切换和实例级兼容矩阵
4. Prompt 版本/实验、Tool Input Contract、Knowledge/pgvector、Docker Sandbox、Trace/回放与 Guardrails
5. Tenant/Organization/Workspace/Project、JWT scope、RBAC 和 PostgreSQL RLS
6. 分布式 Run 控制面、公平队列、优先级、背压、lease、heartbeat、重试和优雅停机
7. LLM/Tool/MCP/Sandbox/Delegation 统一用量、成本、预算、告警和调用前熔断
8. Flyway 双库迁移、CI、Registry/协议/稳定性/故障注入测试，以及真实双服务 HTTP + Chromium 浏览器 E2E
9. Workflow 非法图显式失败与节点级 Recovery，上下文策略、会话恢复、Workflow 导航/结果组装和执行状态事务边界已独立
10. Agent 自适应执行策略：支持 LLM 优先、规则优先、仅规则 Decision，以及 direct reply、单 `user_reply` Workflow 的 Planner 快速路径
11. 单次 Agent Run LLM 物理调用硬预算，覆盖 Decision、Planner、Workflow 节点、Reflection、流式失败重试和 Delegation，并可跨并行步骤共享
12. 阶段模型路由：支持按 `decision/planning/reply/reflection/memory/delegation` 配置模型，未配置阶段自动回退默认模型
13. 通用 Tool 基线：时间、计算、知识检索、受控 HTTP、Web 搜索、文档解析、会话工作区和 Docker Sandbox 均为真实实现，并按权限等级分层
14. Tool Capability Pack：支持能力包注册、版本、成员管理、Agent 多包绑定和运行时去重装配，高风险能力不再跟随默认 Tool 范围自动继承
15. MCP 接入模板与 Runtime：支持 Filesystem、PostgreSQL 只读和 GitHub 官方远程 MCP 的配置化发现与安装；stdio Server 固定版本预装，发现端与执行端共享持久化配置，凭据使用环境变量占位符而非明文入库
16. Runtime SDK：TypeScript 已接入管理前端，Java SDK 和独立可执行宿主覆盖 Thread、Run、Event、Approval、Recovery、Artifact 与 Replay，并通过真实 HTTP/SSE Contract Test 和隔离双服务 E2E

## 验收基线

最新 E2E 使用非超级用户和全新双库执行全部 Flyway migration，完成 17 个基线 Task、4 个并发异步 Run，并额外通过 Java SDK 示例创建和完成独立 Run；验证长会话连续性、稳定分流、成本归因、双向租户隔离、预算硬熔断、Runtime Plugin 对账、Capability 审计，以及真实 Runtime Event SDK 消费。

## 后续优先级

1. P0：Kubernetes/多主机压测、故障注入、容量模型、SLO 和恢复演练
2. P0：KMS/Vault、镜像签名、SBOM、依赖漏洞与插件供应链验证
3. P1：真实 LLM/Tool/MCP 供应商认证矩阵和回归环境
4. P1：账单对账、多币种、归档保留策略、合规审计导出
5. P2：批量 Prompt/模型/压缩实验、主动告警与 On-call 集成

这些事项属于生产运营成熟度提升，不应再通过向 `agent-core` 增加领域规则或硬编码 Tool 实现来完成。

## Codex Harness 方向专项改造

已新增 [Codex Harness 启发的运行内核改造计划](./Codex-Harness运行内核改造计划.md)。专项计划坚持现有双服务边界，优先实施统一 Runtime Event Protocol 和无副作用 Replay，再推进 AgentLoopKernel、Runtime Plugin、Capability Policy、双执行模式和 SDK。第一批不替换 Workflow、不删除旧接口、不新增微服务，也不开放会重复外部副作用的真实执行重放。
