# 通用 Agent 平台双服务开发约定

## 1. 结论

本项目采用双服务架构，拆分为以下两个独立后端服务：

1. `agent-core`
2. `registry-center`

两者独立开发、独立启动、独立部署、独立数据库管理。

职责划分原则：

- `agent-core` 负责运行时执行
- `registry-center` 负责注册、配置、发布、发现

不建议将两者做成一个单体服务后期再硬拆。当前阶段可以保持“服务独立、调用简单”，优先通过 `HTTP REST API` 通信，不急于引入复杂微服务治理体系。

---

## 2. 项目目标理解

本项目不是单一业务 Agent，而是一个可扩展的通用 Agent 平台。

平台目标：

1. 提供统一 Agent 执行引擎
2. 提供统一注册中心管理 Agent、Tool、Workflow、Prompt、Knowledge 等资源
3. 支持通过配置快速组装垂直领域 Agent
4. 支持后续扩展 `Memory`、`RAG`、`Multi-Agent`、`Sandbox`、`Approval` 等能力

---

## 3. 双服务职责边界

## 3.1 agent-core 职责

`agent-core` 是执行引擎服务，负责所有运行时行为。

核心职责：

1. 会话管理
2. 上下文构建
3. 决策与规划
4. 任务拆解与执行
5. 工作流调度
6. 工具路由与工具调用
7. 沙盒执行协调
8. 结果反思与失败恢复
9. 记忆沉淀
10. 响应生成
11. 运行日志与执行状态追踪

典型模块建议：

- `conversation`
- `context`
- `decision`
- `planner`
- `task`
- `workflow`
- `tool`
- `sandbox`
- `reflection`
- `memory`
- `response`
- `approval`

## 3.2 registry-center 职责

`registry-center` 是注册中心服务，负责统一管理所有可被平台使用的资源定义。

核心职责：

1. Agent 注册与版本管理
2. Tool 注册与发布
3. Workflow 定义与版本管理
4. Prompt 模板管理
5. Knowledge 元数据管理
6. Sandbox 配置管理
7. 权限模型与策略管理
8. 资源发现、查询、启停、上下线
9. 元数据管理与依赖关系管理

典型模块建议：

- `agent`
- `tool`
- `workflow`
- `prompt`
- `knowledge`
- `sandbox`
- `permission`
- `publish`
- `metadata`

## 3.3 边界判断原则

判断一个功能应该放在哪个服务，按下面规则：

1. 如果它描述“资源长什么样、怎么配置、哪个版本可用”，放 `registry-center`
2. 如果它描述“资源怎么被执行、执行到了哪一步、执行结果如何”，放 `agent-core`

示例：

- Tool 定义、输入输出 Schema、权限配置：放 `registry-center`
- Tool 调用记录、调用耗时、执行结果、失败原因：放 `agent-core`
- Workflow 模板定义：放 `registry-center`
- Workflow 实例执行状态：放 `agent-core`
- Prompt 模板管理：放 `registry-center`
- 本次会话最终使用的 Prompt 与上下文：放 `agent-core`

## 3.4 ExecutionContext 约定

`ExecutionContext` 是 `agent-core` 中一次 Agent 执行所需全部运行时信息的统一上下文对象，不是独立工程，也不是单独服务。

定义原则：

1. `ExecutionContext` 负责汇总本次执行需要的全部消息和运行时现场数据
2. `ExecutionContext` 至少应包含：
   - 当前用户与权限信息
   - 当前会话信息
   - 当前 Agent 快照
   - 当前 Prompt 快照
   - 当前可用 Workflow 列表
   - 当前可用 Tool 列表
   - 当前用户消息
   - 当前 Task 与 TaskStep
   - 已执行步骤记录与中间结果
3. `ExecutionContext` 的职责是统一承载执行数据，不负责直接实现业务逻辑
4. `Tool Router`、`ToolExecutor`、`WorkflowExecutor`、`ResponseAssembler` 等运行时组件都应围绕 `ExecutionContext` 工作

实现约定：

1. `ExecutionContext` 在代码上必须按信息来源拆分构建，不要在一个超长方法中一次性拼装所有字段
2. 建议拆成一组清晰的方法，例如：
   - `resolveCurrentUser()`
   - `resolveConversation()`
   - `resolveAgentSnapshot()`
   - `resolvePromptSnapshot()`
   - `resolveAvailableWorkflows()`
   - `resolveAvailableTools()`
   - `resolveTaskContext()`
   - `resolveExecutionRecords()`
3. `ExecutionContext` 当前阶段用于承载路由、规划和步骤编排所需的候选信息，不要求提前放入目标 Workflow 的完整定义快照
4. 当执行计划实际命中某个 Workflow 时，再由 `WorkflowExecutorService` 按 `workflowId` 即时加载 `Workflow Snapshot`
5. 通过这些独立方法可以清楚表达“本次执行需要哪些信息、这些信息从哪里来”
6. 执行链路开发优先围绕“用户输入 -> 上下文构建 -> 路由/规划 -> Task/Step 执行 -> 结果回写”推进
7. 在执行引擎阶段，具体 Tool 只作为框架验证样例，不应替代通用执行架构本身的开发

决策阶段补充约定：

1. `ExecutionDecision` 阶段默认优先使用规则决策，`LLM` 决策仅作为可选增强能力
2. 当前 `LLM` 决策输入应限定为：
   - `decisionPrompt`
   - `userMessage`
   - `conversationMemory`
   - `userMemory`
   - `recentTaskMemory`
   - `availableTools`
   - `availableWorkflows`
3. `availableTools` 传给决策模型时，应包含最小可路由摘要，例如：
   - `toolCode`
   - `toolName`
   - `toolType`
   - `toolCategory`
   - `description`
   - `metadata.routing`
4. `availableWorkflows` 传给决策模型时，应包含最小可路由摘要，例如：
   - `workflowId`
   - `workflowCode`
   - `workflowName`
   - `workflowType`
   - `workflowCategory`
   - `description`
   - `metadata.routing`
5. 决策阶段默认不传完整 `Agent Prompt`，避免把角色设定、回答风格、输出格式等回复期约束带入路由判断
6. 如确需补充 Agent 侧约束，优先传递与路由相关的精简摘要，不直接传入完整 `promptContext.promptContent()`
7. `Agent Prompt` 主要服务于最终回复生成、Tool 执行输入增强或 Workflow 节点执行，不应默认参与执行分支判断
8. `ExecutionDecision` 只负责判断本次执行命中了哪些资源，不负责定义执行顺序
9. `ExecutionDecision` 的通用返回结构应优先表达为：
   - `decisionType`
   - `reason`
   - `selectedTools`
   - `selectedWorkflows`
10. `selectedTools` 用于表示本次决策选中的 Tool 集合，至少包含：
   - `toolCode`
   - `toolName`
11. `selectedWorkflows` 用于表示本次决策选中的 Workflow 集合，至少包含：
   - `workflowId`
   - `workflowName`
12. `ExecutionPlan` 阶段应由独立 `Planner` 根据 `selectedTools / selectedWorkflows`、用户目标、上下文摘要和约束生成有序 `steps`，统一决定执行顺序、步骤编号和执行链快照
13. `Planner` 默认优先采用 `LLM` 输出结构化计划，但必须限制在决策阶段已选中的资源范围内，并通过服务端做结构、依赖、资源引用与步骤类型校验
14. 当前执行器已正式兼容 `tool`、`workflow`、`reply`、`condition`、`approval`、`handoff` 六类可执行步骤；`start`、`end` 等节点类型仍在 Planner 模型中预留，未接入执行器前不得直接下发执行
15. `condition` 步骤当前同时支持规则模式与 `LLM` 语义判断模式；规则模式推荐在 `step.inputs` 中使用 `keywords`、`keyword`、`availableToolCode` 或固定 `expression` 描述条件
16. 当 `step.inputs.mode = llm`，或提供 `llmCondition / semanticRule`，或提供非固定值 `expression` 时，执行器应调用运行时模型完成语义判断；模型不可用时应显式失败，不允许静默误判
17. 如需控制后续步骤是否执行，Planner 应在后续步骤的 `step.inputs.runWhen` 中声明条件依赖，结构建议为 `{ "conditionStepId": "step_x", "expectedResult": true }`，或同结构数组表示多个 AND 条件
18. `approval` 步骤由执行器直接挂起为待审批状态，不单独调用 Tool 或 Workflow；审批通过后按 `nextPlanStepNo` 从后续计划步骤继续执行
19. 决策阶段不应默认返回带顺序语义的 `plannedSteps`，除非后续明确把“决策即计划”作为单独模式引入

## 3.5 Recovery / Retry 约定

`Recovery / Retry` 当前按“最小可控实现”推进，目标不是一次性做完整恢复系统，而是先把步骤失败后的最小重试规则、状态沉淀和后续扩展边界立住。

当前逻辑：

1. 自动重试当前只对 `tool` 类型步骤开放
2. `workflow`、`direct_reply`、`condition`、`approval` 节点当前不自动重试
3. `tool` 步骤当前固定最多自动重试 `1` 次
4. 第一次执行失败后：
   - 递增 `retry_count`
   - 记录重试日志
   - 重新执行当前 Tool
5. 第二次仍失败时：
   - 当前步骤收敛为最终失败
   - 记录 `failure_type`
   - 记录 `error_message`
6. 步骤最终成功时：
   - `task_step.status = success`
   - `retry_count` 保留实际重试次数
7. 任一步骤最终失败时：
   - `task.status = failed`
   - 当前消息链路结束，不继续后续步骤

失败类型约定：

1. `tool_unavailable`
   - Tool 不存在
   - Tool 当前不可用
   - Agent 当前无可用 Tool 执行器
2. `tool_execution_failed`
   - Tool 已选中但执行时报错
3. `workflow_execution_failed`
   - Workflow 执行阶段报错
4. `direct_reply_failed`
   - 直接回复阶段异常

数据沉淀约定：

1. `task_steps.retry_count` 记录当前步骤真实重试次数
2. `task_steps.output_snapshot` 在失败时应包含：
   - 失败摘要
   - `failure_type`
   - `error_message`
   - `retry_count`
3. 前端执行时间线应展示：
   - 当前步骤状态
   - 当前步骤错误信息
   - 当前步骤重试次数

当前实现说明：

1. 当前 `sendMessage()` 已不再包裹单个大事务
2. `user message`、`task`、`task_step`、失败状态更新按步骤独立提交
3. 因此当某个步骤最终失败时，失败态的 `task / task_step` 可保留用于后续恢复分析
4. 当前已支持按任务首个失败步骤执行最小恢复，恢复时不重跑已成功步骤，而是复用前序成功步骤摘要继续向后执行
5. 恢复前会将失败步骤及其后续步骤归档为 `is_deleted = TRUE`，再写入新的恢复步骤记录，避免同一 `task_id + step_no` 唯一约束冲突
6. 恢复前会校验当前执行计划与失败步骤是否仍然一致，至少校验步骤类型、步骤名称以及目标 `tool/workflow`
7. 恢复后的新步骤输入快照中会写入恢复来源步骤和回放的前序步骤摘要，便于执行时间线直接解释本次恢复依据
8. 当失败步骤类型为 `workflow` 时，当前支持从失败节点继续恢复，失败节点 ID 和已执行节点快照会沉淀到 `recoveryMetadata`
9. 消息创建与策略更新使用短事务；长时间的 Decision / Plan / Workflow / Tool 执行不持有数据库事务；`processing / success / failed / waiting_approval` 状态通过 `ExecutionStatusFlowService` 的 `REQUIRES_NEW` 独立事务提交，保证外层执行失败时 Recovery 现场仍可持久化
10. 当前最小 `Approval` 骨架已接入 `workflow`，当命中 `approval` 节点时，任务与步骤会进入 `waiting_approval` 状态，并生成运行时审批记录
11. 审批通过后，当前支持基于审批节点保存的 `nextNodeId`、已执行节点快照和前序节点结果继续执行
12. 审批拒绝后，当前任务直接结束并收敛为失败态
13. Workflow 不允许静默 fallback：缺少 start 出口、目标节点不存在、条件无匹配分支、节点类型非法、疑似循环或未到达 end 均必须抛出 `WorkflowExecutionException`，并携带失败节点、已执行节点和前序结果用于明确 Recovery
14. `Memory` 注入当前已按执行路径与典型 Tool 场景细化策略：
   - `direct_reply` 默认注入会话摘要、用户偏好、用户目标；命中“继续/刚才/上一步/之前”等续写意图时，再追加最近任务记忆
   - `DOC_SEARCH` 优先注入会话摘要、最近任务摘要、用户关注点、用户目标
   - `SCORE_ANALYSIS` 优先注入用户长期事实、用户目标、用户偏好、最近任务摘要
   - `TIME_INFO` 仅注入最小用户偏好，不注入最近任务摘要，避免无关记忆污染
   - `workflow` 节点默认注入会话摘要、用户目标、用户关注点和最近任务摘要
15. 当前步骤输入快照中必须沉淀：
   - `memoryStrategy`
   - `selectedMemoryItems`
   - `resolvedInputText`
   便于后续从执行时间线直接判断“本步骤为什么选了这些记忆”
15. 审批相关恢复规则当前补充如下：
   - 若任务仍存在 `pending` 审批记录，不允许走通用 `resume`，必须先完成审批动作
   - 若任务已经被审批拒绝，不允许再通过通用 `resume` 继续执行
   - 审批通过前，必须校验审批步骤状态、审批节点 `nodeId / nodeName` 和待审批快照仍一致
   - 审批通过后若继续执行再次失败，任务与会话状态必须显式回写为 `failed`
   - 审批继续执行写入的新步骤输入快照中，必须包含 `approvalReplay`，用于说明本次执行由哪个审批节点放行
16. 恢复前校验逻辑应独立收口到专门组件，当前统一由 `RecoveryValidationService` 负责：
   - 通用失败恢复前的审批状态校验
   - 恢复计划与历史失败步骤的一致性校验
   - 审批继续执行前的审批节点元数据校验
17. `workflow` 恢复规则当前进一步约定：
   - 恢复上下文必须提供有效的 `resumeNodeId`
   - `resumeNodeId` 必须仍存在于当前 Workflow 定义中，且不能指向 `start`
   - 恢复上下文中的前序节点若已不存在或与恢复目标节点冲突，应拒绝恢复
   - Workflow 输出快照中应包含 `recovery` 元数据，至少记录：
     - `resumeMode`
     - `resumeNodeId`
     - `resumeNodeType`
     - `replayedNodeCount`
     - `executedNodeCountBeforeResume`
18. `Memory` 注入规则当前进一步约定：
   - 记忆“选哪些内容”由 `MemorySelectorService` 负责
   - 记忆“保存哪些内容”当前先由规则提取候选项，再可选交给 `LLM` 做归一化/压缩，最终仍由规则层负责去重合并与保存
   - `LLM` 归一化必须是可开关的增强层，调用失败时必须自动回退到纯规则结果
19. `Approval / Recovery` 状态机边界当前进一步约定：
   - 通用 `resume` 仅允许 `task.status = failed` 且首个失败步骤 `status = failed` 的任务进入
   - `approve` / `reject` 仅允许 `task.status = waiting_approval` 的任务进入
   - 审批记录仅允许 `approval.status = pending` 时被通过或拒绝
   - 审批步骤仅允许 `task_step.status = waiting_approval` 时继续审批动作
   - 以上状态边界应统一收口到专门组件，当前由 `ApprovalRecoveryStateMachineService` 负责，避免散落在 `ConversationService`
   - 候选记忆项“从 ExecutionContext 中怎么提取”由 `MemoryItemCollectorService` 负责
   - Prompt、记忆、前序结果“如何拼装成最终输入文本”由 `MemoryInjectionPolicyService` 负责
   - `MemorySelectorService` 仅负责策略选择，不再同时承担候选项提取细节
   - `MemoryInjectionService` 仅负责串联选择与注入，不再同时承担具体拼装细节
   - direct reply、Tool、Workflow 三类执行路径应分别走独立的输入拼装方法，避免后续继续堆积在一个超长方法中
19. `Workflow` 执行上下文当前进一步约定：
   - 节点执行时应统一构建 `WorkflowNodeExecutionContext`
   - 节点快照中应统一包含：
     - `nodeId`
     - `nodeType`
     - `nodeName`
     - `previousNodeResults`
     - `runtimeVariables`
   - `runtimeVariables` 应承载 Workflow 运行时公共变量，例如：
     - `workflowCode`
     - `workflowName`
     - `userMessage`
     - `availableToolCodes`
     - 恢复执行时的 `resumeMode / resumeNodeId`
   - Workflow 最终输出快照中应汇总 `runtimeVariables`，便于后续恢复、审计和前端时间线展示
20. 执行主流程当前进一步约定：
   - `ConversationService` 负责会话入口、权限边界、数据装载与结果回写
   - 步骤编排、步骤执行、步骤重试、审批挂起处理应统一收口到 `ExecutionOrchestratorService`
   - direct reply、单步 Tool、多步计划、Workflow 执行的最终文本响应应统一收口到 `ExecutionResponseAssemblerService`
   - task / conversation 的主流程状态回写应统一收口到 `ExecutionStatusFlowService`
   - `ConversationService` 不再承载旧的步骤编排、步骤执行、响应拼装和重试细节方法，避免重新膨胀为超大服务
   - 后续新增执行路径时，优先扩展编排服务，不要继续把主流程堆回 `ConversationService`

后续增强方向：

1. 增加可重试异常白名单
2. 为不同步骤类型配置不同重试次数
3. 增加重试间隔与退避策略
4. 继续增强恢复逻辑，例如更细粒度的上下文回放、恢复策略和恢复前资源校验
5. 已支持人工审批后继续执行，并支持审批拒绝后终止任务

## 4. 技术栈约定

## 4.1 前端技术

统一前端技术栈：

- `Vue 3`
- `TypeScript`
- `Vite`
- `Pinia`
- `Vue Router`
- `Element Plus`
- `axios`

前端建议先做一个统一管理后台，不拆成两个前端站点。通过菜单区分：

1. 运行态页面
2. 注册中心配置页面

## 4.2 后端技术

两个后端服务统一使用：

- `Java 17`
- `Spring Boot 3.x`
- `Spring Web`
- `Spring Validation`
- `Spring Security`
- `MyBatis-Plus`
- `Spring Data Redis`
- `LangChain4j`

可选能力：

- 定时任务：`Spring Task`

## 7. 服务间通信约定

## 7.1 当前阶段建议

前期统一采用 `HTTP REST API` 通信。

不建议第一阶段直接引入：

- 分布式事务
- 服务网格
- 复杂注册发现框架
- 过重消息中间件架构

## 7.2 调用方向

主要方向建议为：

1. `frontend-web -> agent-core`
2. `frontend-web -> registry-center`
3. `agent-core -> registry-center`

原则：

- `agent-core` 可读取 `registry-center`
- `registry-center` 不直接依赖 `agent-core` 运行时数据

## 7.3 通信内容

`agent-core` 从 `registry-center` 获取：

1. Agent 配置
2. Tool 定义
3. Workflow 模板
4. Prompt 模板
5. 权限与资源配置
6. Sandbox 配置

## 7.4 缓存策略

执行期不要每一步都实时查询注册中心。

建议：

1. 启动时预热关键配置
2. 常用资源本地缓存
3. 定时刷新或基于版本号刷新
4. 读取失败时允许短期降级使用缓存

## 8. 认证与权限约定

## 8.1 基本原则

认证、用户、角色、权限定义统一收口到 `registry-center`。

职责划分：

1. `registry-center` 负责登录认证、用户管理、角色管理、权限配置、Token 签发
2. `agent-core` 负责消费 Token、校验 Token，并执行运行时权限判断

不建议两个服务分别维护独立账号体系，也不建议由 `agent-core` 单独签发一套业务 Token。

## 8.2 Token 职责边界

`registry-center` 负责：

1. 用户登录
2. Token 签发
3. Token 刷新
4. 当前用户信息查询
5. 角色与权限定义

`agent-core` 负责：

1. 校验请求中的 Token
2. 识别当前用户身份
3. 校验当前用户是否具备执行某个 Agent、Tool、Workflow、Approval 的权限
4. 将用户身份写入会话、任务、审批、日志等运行时上下文

## 8.3 实现建议

建议采用统一的 `JWT` 方案。

要求：

1. 两个服务使用统一的 `issuer`
2. 两个服务使用统一的签名规则
3. Token 中至少包含用户标识、租户标识、角色或权限摘要
4. `agent-core` 本地完成 Token 校验，不依赖每次远程回源校验

说明：

1. 登录认证属于平台管理能力，归 `registry-center`
2. 运行时执行权限属于业务执行能力，归 `agent-core`
3. 即使权限来源在 `registry-center`，执行态仍要在 `agent-core` 落地拦截

## 8.4 权限分类建议

建议区分以下几类权限：

1. 后台管理权限
2. 资源配置权限
3. 运行时执行权限
4. 审批权限

示例理解：

1. 是否允许登录系统，属于认证问题
2. 是否允许管理 Tool、Workflow、Prompt，属于注册中心管理权限
3. 是否允许执行某个高风险 Tool，属于 `agent-core` 运行时权限
4. 是否允许审批某个任务节点，属于审批权限

## 10. 编码规范

## 9.1 文件编码

统一要求：

1. 所有文件使用 `UTF-8`
2. 新增文件优先 `UTF-8 without BOM`
3. 换行符统一 `LF`
4. 中文注释、中文日志、中文提示必须可正常显示

## 9.2 Java 编码规范

命名要求：

- 类名：`UpperCamelCase`
- 方法名：`lowerCamelCase`
- 字段名：`lowerCamelCase`
- 常量：`UPPER_SNAKE_CASE`
- 包名：全小写

开发要求：

1. 方法职责单一
2. 不随意新增复杂抽象层
3. 不擅自修改公共方法签名
4. 超过 4 到 5 个参数时优先封装 DTO
5. 避免超长方法和深层嵌套判断

## 9.3 注释规范

要求：

1. `public` 方法建议加注释
2. 核心业务方法必须加注释
3. 复杂判断、状态流转、重试逻辑、路由逻辑必须加注释
4. 注释说明“为什么”，不要只重复代码含义
5. `model`、`vo`、`dto` 中的字段必须加注释
6. `record` 类型中的字段说明必须通过字段前注释或 `@param` 明确标注

建议：

- 类注释：描述职责边界
- 方法注释：描述用途、关键参数、返回值、异常场景
- 字段注释：描述字段语义、状态值含义、是否为快照或展示字段
- 关键代码块注释：描述特殊规则、状态判断原因、兼容逻辑

## 9.4 前端编码规范

要求：

1. `api` 与页面逻辑分离
2. 类型定义统一维护在 `types`
3. 页面级组件放 `views`
4. 可复用组件放 `components`
5. 不要把请求、类型、页面逻辑全部堆在一个 `.vue` 文件中

## 11. Agent 平台专项规范

## 10.1 配置优先

以下内容优先配置化，不建议硬编码：

1. Agent 定义
2. Prompt 模板
3. Tool 清单
4. Workflow 模板
5. 权限规则
6. Sandbox 规则

## 10.2 Tool 规范

每个 Tool 至少包含以下字段：

- `code`
- `name`
- `description`
- `tool_type`
- `tool_category`
- `input_schema`
- `output_schema`
- `permission`
- `timeout`
- `enabled`
- `version`

说明：

1. `tool_type` 表示能力类型，例如 `search`、`knowledge`、`analysis`
2. `tool_category` 表示场景分类，例如 `platform_default`、`education`、`github`
3. 平台默认 Tool 与行业 Tool 当前通过 `tool_category` 区分

Tool 执行记录至少包含：

- `task_id`
- `step_id`
- `tool_code`
- `request_payload`
- `response_payload`
- `status`
- `error_message`
- `duration_ms`

## 10.3 Workflow 规范

Workflow 定义在 `registry-center`，执行实例在 `agent-core`。

要求：

1. 定义与实例分离
2. 支持步骤顺序
3. 支持条件分支
4. 支持失败重试
5. 支持人工审批节点扩展
6. 应支持 `workflow_type`、`workflow_category` 资源分类

Workflow 归属约定：

1. `registry-center` 负责 Workflow 的编排定义与版本管理
2. `agent-core` 负责 Workflow 的执行、调度、状态推进与结果记录

边界说明：

1. 流程结构、节点定义、节点关系、节点配置，属于编排定义，放 `registry-center`
2. 某次流程运行到哪个节点、节点执行成功或失败、重试次数、审批结果，属于运行时数据，放 `agent-core`

第一阶段节点设计建议：

1. 节点可以以 `tool` 节点为主
2. 但不要把 Workflow 限死为“只能由 Tool 节点组成”
3. 至少预留以下节点类型扩展能力：
   - `tool`
   - `condition`
   - `approval`
   - `start`
   - `end`

说明：

1. `tool` 节点负责调用具体工具，是第一阶段最核心的执行节点
2. `condition` 节点负责流程分支判断，避免后期因分支能力缺失推翻流程设计
3. `approval` 节点负责人工确认类场景，便于后续接入高风险操作审批
4. `start` 和 `end` 节点用于明确流程入口和出口，便于流程定义统一

实现原则：

1. 节点应抽象为通用节点模型，不要与 Tool 实体做硬编码绑定
2. 当节点类型为 `tool` 时，再关联具体 `tool_code` 或工具标识
3. `agent-core` 执行时应按节点类型解释执行，而不是只按 Tool 调用处理
4. 第一阶段可以先重点实现 `tool` 节点执行链路，其他节点类型先预留接口和扩展位

资源分类建议：

1. `workflow_type` 用于表达流程能力类型，例如 `orchestration`、`planning`、`chat`
2. `workflow_category` 用于表达场景分类，例如 `platform_default`、`education`、`github`
3. 平台默认 Workflow 与行业 Workflow 当前通过 `workflow_category` 区分

Agent Tool 范围约定：

1. `inherit_default`：仅继承平台默认 Tool 集
2. `inherit_and_append`：继承平台默认 Tool 集，再追加 Agent 自定义 Tool
3. `custom`：完全使用 Agent 自定义 Tool 集，不继承默认 Tool

资源字典管理约定：

1. `tool_type`
2. `tool_category`
3. `workflow_type`
4. `workflow_category`
5. `prompt_type`
6. `prompt_category`
7. `permission_level`
8. `agent_tool_scope_mode`

以上字段从当前阶段开始不再建议自由输入，应统一接入平台字典管理。

执行要求：

1. 后端接口写入前必须校验字典项是否合法
2. 前端新增、编辑、查询界面优先使用字典下拉
3. 业务表仍保存英文编码值，不保存中文展示名
4. 平台应提供统一字典管理页面和字典接口

## 10.4 Memory 与 Context 区分

必须区分：

1. `Context`：当前任务临时使用的上下文
2. `Memory`：可沉淀、可复用的长期信息

不建议第一版将两者混成一个大字段，否则后期 RAG 和记忆管理会非常混乱。

## 12. 日志、异常与审计规范

## 11.1 日志规范

统一使用 `Slf4j`。

关键流程必须记录日志：

1. 会话创建
2. 任务规划
3. 工作流执行

5. 沙盒执行
6. 审批动作

日志禁止输出：

- 密码
- `token`
- 密钥
- 完整敏感入参

## 11.2 异常处理规范

要求：

1. 全局异常统一处理
2. 业务异常与系统异常分离
3. 前端返回信息可读但不暴露堆栈
4. LLM 调用失败、工具失败、沙盒失败要分类记录

## 11.3 审计规范

以下动作建议记录审计日志：

1. Agent 发布与下线
2. Tool 注册与变更
3. Workflow 发布
4. 权限配置变更
5. 高风险工具调用
6. 审批通过与拒绝
