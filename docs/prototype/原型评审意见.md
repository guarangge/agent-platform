# 通用 Agent 平台 MVP 原型评审意见

## 1. 结论

本次采用多 Agent 评审，分别从产品、开发、数据库、测试 4 个视角对当前原型进行检查。

综合结论：

1. 当前原型方向正确，已经具备进入 MVP 开发的基础
2. 但不建议直接进入完整页面开发、数据库建模和接口实现
3. 建议先完成一轮“小范围原型修正和规则补充”，再正式进入开发

当前建议状态：

`可开发，但需先修正关键问题`

## 3. 主要优点

### 3.1 平台方向清晰

1. 原型已经清楚区分 `registry-center` 和 `agent-core`
2. 管理类页面与会话执行页边界基本成立
3. 整体符合“双服务平台 + 统一前端后台”的设计方向

### 3.2 MVP 范围总体克制

1. 第一版没有直接上复杂拖拽编排器
2. 第一版没有直接上复杂监控大盘
3. 第一版聚焦登录、资源管理、权限主链路、会话执行入口，范围可控

### 3.3 权限主链路合理

当前原型已经收敛成：

1. 用户
2. 角色
3. 用户绑定角色
4. 角色绑定 Agent

这比“用户直接绑定 Agent”更稳，后续无论是产品表达、数据库建模，还是测试设计，都更容易落地。

### 3.4 资源关系具备最小闭环

原型已经表达出：

1. `Agent` 关联 `Prompt`
2. `Agent` 关联 `Workflow`
3. `Agent` 关联 `Tool`
4. 会话与 `Agent`、消息之间存在基础运行关系

这说明当前原型已经不是纯展示页，而是具备继续拆设计和实现的基础。

### 3.5 文档与页面原型一致性较好

1. 原型说明与 HTML 预览整体表达一致
2. 页面目标、区块划分、关键操作基本能对应
3. 便于后续继续拆开发任务和测试点

---

## 4. 主要问题

### 4.1 权限管理页信息架构不够清晰

当前问题：

1. 文档中写了 `用户管理`、`角色管理`、`用户绑定角色`、`角色绑定 Agent`
2. HTML 原型里更像是混合主表 + 关系预览
3. 当前表达容易让用户分不清“当前正在管理用户还是角色”
4. “用户绑定角色”和“角色绑定 Agent”属于两个不同授权动作，不适合混在一个同级主视图里

### 4.2 会话页的 Agent 选择规则还没定清

当前存在两种入口表达：

1. 从 `Agent 管理页` 进入会话并带入当前 Agent
2. 从首页点击“开始会话”后再选择 Agent

还没明确：

1. 会话创建后是否允许切换 Agent
2. 会话是否必须固定绑定一个 Agent
3. 未绑定 Agent 的用户进入会话页时如何处理

这是业务规则问题，不应拖到开发阶段再决定。

### 4.3 Dashboard 职责偏多

当前首页同时承担：

1. 导航入口
2. 概览卡片
3. 最近记录
4. 快速新建动作

对于 MVP 来说略满，容易做成信息很多但不聚焦的页面。

### 4.4 后台管理权限边界没有写清

当前原型重点解决了“谁能使用哪个 Agent”，但还没有明确：

1. 谁能管理 Tool
2. 谁能管理 Workflow
3. 谁能管理 Prompt
4. 谁能管理用户和角色
5. 普通使用者是否能看到注册中心菜单

也就是说，当前更像“Agent 使用授权模型”，还不是完整的“后台访问权限规则”。

### 4.5 会话页定位还不够收敛

当前会话页已经出现了：

`Planning -> Tool Running -> Response`

这会让人理解成它既是聊天页，也是任务执行监控页。  
MVP 第一版可以保留轻量执行反馈，但不应该让用户误以为这里会展示完整任务树和完整 Tool 调用链。

### 4.6 数据约束规则还不够明确

当前原型虽然能支撑主链路，但这些约束还没定：

1. 一个用户是否允许绑定多个角色
2. 一个角色是否允许绑定多个 Agent
3. 关系是否允许重复绑定
4. 角色停用后历史关系是否保留
5. Agent 停用后角色绑定关系是否保留但不生效
6. 会话是否固定只属于一个用户和一个 Agent

这些问题不先定，后面数据库设计很容易返工。

### 4.7 状态流转、空状态和异常状态不够完整

当前问题主要在：

1. `草稿`、`启用`、`停用`、`已发布` 的资源状态规则还没统一
2. 会话发送失败、超时、无响应、重复发送等异常链路缺少说明
3. 无数据页面、无角色、无 Agent、无权限等空状态说明不足
4. Token 过期、授权被撤销等运行时权限失败路径未定义

这些问题会直接影响测试设计和前端交互实现。

## 5. 优化建议

### 5.1 权限管理页改成“两层结构”

建议调整为：

1. 一级页签只保留：`用户管理`、`角色管理`
2. 在用户详情里执行“绑定角色”
3. 在角色详情里执行“绑定 Agent”

这样比把“用户、角色、关系绑定”全部并列在一个主界面上更清楚。

### 5.2 先明确会话入口规则

建议 MVP 直接定为：

1. 从 `Agent 管理页` 进入会话时，默认带入当前 Agent
2. 从首页点击“开始会话”时，进入会话页后必须先选择 Agent
3. 会话创建后，本轮会话不允许切换 Agent
4. 一个会话只绑定一个 Agent

这套规则最稳，也最容易落库和实现。

### 5.3 Dashboard 收敛为“导航优先”

建议首页第一版只保留：

1. 快捷入口
2. 4 到 6 个核心统计卡片
3. 最近会话或最近操作二选一

不建议第一版同时放过多运营类记录。

### 5.4 明确后台访问权限规则

建议先补一条平台级规则：

1. 平台管理员：可访问全部管理页和会话页
2. 运营角色：可访问部分管理页和会话页
3. 普通使用者：默认只进入会话页，不进入注册中心管理页

先用角色级菜单访问控制兜底，后续再细化资源级权限。

### 5.5 会话页定位为“聊天执行入口”

建议保留轻量执行反馈，但文案和原型说明中明确：

1. 当前只展示简要执行状态
2. 不展示完整任务树
3. 不展示完整 Tool 调用链
4. 不展示完整恢复重试细节

### 5.6 先补约束和规则，不急着建表

开发前建议先补清以下规则：

1. 用户、角色、Agent 关系唯一性规则
2. Agent 与 Tool / Workflow / Prompt 的关联约束
3. 会话是否固定绑定 Agent
4. Workflow 节点摘要的存储策略
5. 各资源状态枚举和状态流转规则

### 5.7 补充空状态、异常状态和权限失败路径

建议在原型说明中补齐以下内容：

1. 未登录
2. 已登录无角色
3. 已登录有角色但无 Agent
4. 仅查看权限无编辑权限
5. Token 过期
6. 授权被撤销
7. 页面无数据
8. 会话发送失败 / 超时 / 空响应 / 重试

---

## 6. 建议的开发前置决策

正式进入开发前，建议先确认以下事项：

1. 权限页最终是否改成“用户管理 + 角色管理，两边各自详情绑定”
2. 会话是否固定 Agent，且创建后不允许切换
3. Dashboard 第一版是否收敛为导航优先
4. 后台管理权限先是否由管理员角色统一兜底
5. `Tool` / `Workflow` / `Prompt` 的优先级是否低于登录、首页、Agent、权限、会话

---

## 7. 是否可以进入开发

综合结论：

1. 可以进入下一阶段
2. 但建议先进入“原型修正 + 规则补充 + 详细设计”阶段
3. 不建议现在直接进入完整页面开发、接口开发和数据库建表

建议推进顺序：

1. 先修正原型结构
2. 补规则说明
3. 再拆数据库设计和接口设计
4. 最后开始正式开发

一句话总结：

**这版原型主方向是对的，可以继续往下做；但在权限页结构、会话规则、后台权限边界、状态与异常规则这几项补清前，不建议直接开工实现。**
