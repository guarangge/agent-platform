# 双执行模式规范

## 1. 当前结论

M5 八个纵向切片已冻结 Agent 双执行模式配置、运行时路由和 Interactive Loop 硬预算契约，并完成最小循环控制器、审批恢复、生产路由 Adapter、同步与异步真实 E2E、灰度指标与紧急回滚：

1. `workflow_plan`：继续使用现有 Decision、Planner、Plan、Step 和 Workflow 确定性链路
2. `interactive_loop`：作为下一阶段动态 Tool Loop 的稳定模式编码
3. 真实 `interactive_loop` 已具备独立 Feature Flag 与稳定灰度能力，但默认关闭并回退到 `workflow_plan`
4. 现有 Agent 未声明模式时默认使用 `workflow_plan`，不改变历史执行行为
5. Interactive Loop 控制器已串联结构化 Action、预算、Tool Router、Capability Policy 和停止事件，并通过独立 Kernel Adapter 接入 Gateway
6. Capability 审批挂起前保存独立 Loop Checkpoint，通过后只重放挂起 Tool，再从下一轮继续
7. Catalog 安装的 MCP Tool 会按远程 operation 初始化最低安全声明；Core 对旧快照仅做风险升级兜底，明显写操作不能因空声明绕过审批
8. 异步审批恢复会在原 Run 事件序列追加新终态；运行中取消在后续 LLM/Tool 边界生效，不会继续启动下一次调用

## 2. Registry 配置契约

Agent 通过 `metadata.executionPolicy` 配置模式：

```json
{
  "executionPolicy": {
    "defaultMode": "workflow_plan",
    "allowedModes": ["workflow_plan", "interactive_loop"]
  }
}
```

约束：

1. `defaultMode` 仅允许 `workflow_plan / interactive_loop`
2. `allowedModes` 必须是非空且无重复的字符串数组
3. `allowedModes` 必须包含 `workflow_plan`，作为安全回退路径
4. `allowedModes` 必须包含 `defaultMode`
5. 两个字段均未声明时按历史 Agent 处理，默认 `workflow_plan`

## 3. 当前路由顺序

运行时按以下优先级确定 `effectiveMode`：

1. 已选择 Workflow：强制 `workflow_plan`，原因 `workflow_selected`
2. Plan 含 Approval 节点：强制 `workflow_plan`，原因 `approval_required`
3. 默认模式不在允许集合：回退 `workflow_plan`，原因 `mode_not_allowed`
4. 请求 `interactive_loop` 但独立开关关闭、白名单或百分比灰度未命中：回退 `workflow_plan`，记录具体灰度原因
5. 请求 `interactive_loop` 且灰度命中：使用 `interactive_loop_kernel_v1`
6. 其余情况使用 Agent 默认模式，原因 `agent_default`

现有 `ExecutionModeStrategy` 仍只负责 Kernel Adapter 灰度，不代表上述业务执行模式，两者不可混用。

## 4. Runtime Event

每次进入执行网关时，在当前线程已经绑定 Run 的情况下发布 `run.mode.selected`：

```json
{
  "taskId": 1001,
  "requestedMode": "interactive_loop",
  "effectiveMode": "workflow_plan",
  "allowedModes": ["workflow_plan", "interactive_loop"],
  "reason": "interactive_loop_rollout_excluded",
  "fallback": true,
  "rolloutBucket": 88
}
```

事件只记录模式选择事实，不包含用户输入、Prompt、Tool 参数或模型思维链。

## 5. 实现详情

### 5.1 硬预算配置

```json
{
  "executionPolicy": {
    "maxLlmCallsPerRun": 6,
    "interactiveLoop": {
      "maxIterations": 12,
      "maxLlmCalls": 6,
      "maxToolCalls": 16,
      "maxTokens": 50000,
      "maxCostAmount": 5.00,
      "duplicateToolCallLimit": 2
    }
  }
}
```

`maxLlmCalls` 不能超过整次 Run 的 `maxLlmCallsPerRun`。Core 对历史非法配置使用安全默认值，并始终取 Loop 与 Run 中更严格的 LLM 上限。全局 `CostGovernance` 继续作为周期预算和实际用量账本，不被局部预算替代。

### 5.2 原子消费与停止原因

预算状态机在 LLM/Tool 真正调用前判断并消费额度，拒绝的调用不增加计数。相同 `toolCode + parameterHash` 达到重复阈值后停止；安全快照只输出唯一指纹数量，不输出 Tool 参数、参数哈希或完整指纹。

稳定停止原因包括：

1. `completed`
2. `max_iterations`
3. `max_llm_calls`
4. `max_tool_calls`
5. `max_tokens`
6. `max_cost`
7. `duplicate_tool_call`
8. `capability_policy`
9. `approval_required`
10. `cancelled`
11. `failed`

首次停止原因不可覆盖。循环控制器接入后统一发布 `run.loop.stopped`，携带停止原因、已消费额度和预算上限，不携带用户输入或调用指纹。

### 5.3 最小循环控制器

模型每轮只能返回以下两类结构化 Action：

```json
{"action":"tool_call","toolCode":"TOOL_CODE","arguments":{}}
```

```json
{"action":"final_answer","content":"给用户的最终回复"}
```

控制器执行顺序固定为：

1. 消费迭代额度
2. 构建不含认证信息的 Tool 清单和最近 12 条有界 Observation
3. 估算本次输入与最大输出 Token，并按当前模型价格估算成本
4. 原子占用 Loop LLM、Token、成本预算
5. 调用现有 `RuntimeLlmGatewayService` 并严格解析单个 JSON Action
6. 校验 Tool 必须属于 `ExecutionContext.availableTools`
7. 对规范化参数 JSON 计算 SHA-256，消费 Tool 和重复指纹额度
8. 通过现有 `ToolRouterService` 执行，因此继续经过 Capability Policy、Approval、Side Effect、CostGovernance 和 Runtime Event
9. 将 Tool 结果压缩为有界 Observation，继续下一轮；`final_answer` 或任一停止边界结束循环

Action 协议不包含 rationale 字段，不要求也不保存模型思维链。Tool 认证配置不会进入 Prompt；Observation 摘要和正文分别限制为 4000 字符。

Capability 审批命中时先发布 `run.loop.stopped(stopReason=approval_required)`，再原样抛出既有 `ApprovalRequiredException`。越权 Tool 和 Capability 阻断以 `capability_policy` 停止，不调用 Provider。普通 Tool 执行失败作为 Observation 返回模型决定下一步。

### 5.4 审批 Checkpoint 与恢复

`interactive_loop_checkpoints` 与 Plan 的 `task_execution_checkpoints` 分离，保存：

1. 原始预算策略、累计 Iteration/LLM/Tool/Token/成本和不可逆 Tool 指纹
2. 审批前已完成的有界 Observation
3. 触发审批且尚未完成的 Tool Action
4. 审批节点、`toolCallId`、`parameterHash` 和 Trace 绑定

恢复请求必须为 `approved`，且节点、调用 ID、参数哈希和 Trace 全部一致。恢复时不重新请求模型，也不再次消费挂起 Tool 的调用额度；只在 `CapabilityApprovalContext` 中重放该 Tool。Tool 形成成功、不可用或失败 Observation 后，Checkpoint 单向转为 `restored`，控制器从下一轮继续。历史成功 Tool 不会重放，重复调用指纹计数也不会丢失。

### 5.5 Kernel Adapter 与独立灰度

Core 配置如下，默认值不会改变现有 Agent 行为：

```yaml
core:
  runtime:
    interactive-loop:
      enabled: false
      rollout-percent: 0
      agent-ids: []
      project-ids: []
```

对应环境变量为 `CORE_INTERACTIVE_LOOP_ENABLED / CORE_INTERACTIVE_LOOP_ROLLOUT_PERCENT /
CORE_INTERACTIVE_LOOP_AGENT_IDS / CORE_INTERACTIVE_LOOP_PROJECT_IDS`。Project 白名单优先于 Agent 白名单；未配置 Agent
白名单时才使用稳定百分比分桶。稳定分桶只依赖 `agentId + projectId`，服务重启后结果不变。

`interactive_loop_kernel_v1` 使用原 Plan 当前起始步骤作为持久化锚点，但不按 Plan 顺序调用 Tool。Adapter 负责复用现有
Task Step、ApprovalCoordinator 和通用 Plan Checkpoint；Loop Controller 负责动态 Action、预算和 Loop Checkpoint。
因此审批仍在对话窗口展示，批准后既有恢复入口会加载原 Plan，再由 Adapter 恢复挂起 Action。

### 5.6 本地灰度 E2E

本地对白名单 Agent 7 开启灰度，已验证：

1. `TIME_INFO` 真实 Tool Loop 成功；预算不足时按 `max_tokens` 在调用前停止
2. 历史 MCP `write_file` 的空能力声明已由 Flyway 回填为 `filesystem.write / irreversible`
3. Tool 在审批前没有产生文件；会话页自动弹出“高风险操作需要审批”
4. 点击“通过并继续”后弹窗关闭，原 `toolCallId` 对应 Loop Checkpoint 转为 `restored`
5. 仅重放挂起的 Tool，目标文件写入成功，并在同一对话生成最终回复

默认 Feature Flag 和百分比灰度仍关闭；本地 E2E 通过后，继续验证异步 Run、流式事件与取消边界。

### 5.7 异步 Run 与协作式取消

本地异步灰度已验证：

1. 首次执行按 `run.queued -> run.started -> run.waiting` 挂起，审批、Loop 和 Tool 事件全部关联同一 `run_code`
2. 审批通过后从原游标继续产生 `approval.resolved`、Tool 调用和唯一 `run.completed`，重复状态同步不重复发布终态
3. SSE 在 `run.waiting` 关闭后可使用最后 `sequenceNo` 重新订阅，恢复后的终态不会丢失
4. Loop 在每轮开始、LLM 返回后和 Tool 返回后同时检查线程中断与数据库 `cancel_requested`
5. 取消命中时发布 `run.loop.stopped(stopReason=cancelled)`，不再启动下一次 LLM 或 Tool；Task 进入 `cancelled`，当前 Step 以 `failureType=cancelled` 结束，Run 最终发布 `run.cancelled`
6. 取消是关闭终态，不进入 Worker 重试；普通 Tool 失败继续形成 Observation，Capability 审批继续由 Checkpoint 恢复

默认 Feature Flag 和百分比灰度仍关闭；异步边界验收通过后，继续收敛灰度指标与回滚操作。

### 5.8 灰度指标与紧急回滚

1. `CORE_INTERACTIVE_LOOP_KILL_SWITCH=true` 的优先级高于总开关、白名单和百分比，新 Run 统一回退 `workflow_plan`
2. `agent.runtime.interactive.loop.route` 记录灰度命中/回退与有限原因，不使用 Agent、Project 或用户作为 Tag
3. `agent.runtime.interactive.loop.stop` 记录停止原因，Distribution Summary 记录迭代、LLM、Tool、Token 和计价金额消耗
4. Actuator 暴露需要认证的 `metrics` 端点，不放开匿名访问
5. 灰度验收采用终态唯一、审批不绕过、无重复副作用、失败/预算停止率和取消不重试六类门禁
6. 完整发布批次、SQL 审计、熔断与恢复步骤见 `docs/runtime/InteractiveLoop发布与回滚.md`

M5 当前范围已完成。默认 Feature Flag 和百分比仍关闭，扩大灰度必须满足 Runbook 门禁。
