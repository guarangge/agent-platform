# 通用 Agent 平台数据库设计

## 1. 结论

本项目数据库按双服务边界拆分：

1. `registry-center` 独立数据库
2. `agent-core` 独立数据库

当前设计原则：

1. 先覆盖 MVP 稳定范围
2. 先做主链路，不先做过重扩展
3. 资源定义放 `registry-center`
4. 运行数据放 `agent-core`
5. 状态、关系、索引规则先明确，再进入建表实现

当前落地说明：

1. `registry-center` 当前真实落库已覆盖 `users`、`roles`、`user_role_rel`、`agents`、`tools`、`tool_providers`、`tool_provider_instances`、`tool_bindings`、`workflows`、`prompts`、`agent_tool_rel`、`agent_workflow_rel`、`role_agent_rel`、`guardrail_policies`
2. Flyway 初始化脚本位置：`registry-center/src/main/resources/db/migration/V1__registry_center_baseline.sql`
3. 认证模块当前已切换为真实 `PostgreSQL` 查询，不再使用内存演示用户
4. Workflow 模块当前已切换到真实 `PostgreSQL` 查询，并已完成首轮联调验证
5. Prompt 模块当前已切换到真实 `PostgreSQL` 查询，并已完成首轮联调验证
6. `agent-core` 当前真实落库已覆盖 `conversations`、`messages`、`conversation_memories`、`user_memories`、`task_memory_snapshots`、`tasks`、`task_plans`、`task_plan_steps`、`task_steps`、`approvals`、`task_traces`、`task_delegations`、`guardrail_policy_hits`
7. 两个服务统一使用 Flyway 管理数据库版本；已有实例以 `2026071500` 建立 baseline，全新实例从各服务 `db/migration/V1` 初始化，后续禁止修改已执行迁移脚本
7. Flyway 初始化脚本位置：`agent-core/src/main/resources/db/migration/V1__agent_core_baseline.sql`

## 2. 数据库拆分原则

### 2.1 registry-center

负责存储：

1. 用户
2. 角色
3. 用户角色关系
4. Agent 定义
5. Tool 定义
6. Workflow 定义
7. Prompt 定义
8. 角色 Agent 关系
9. 资源状态与版本元数据

### 2.2 agent-core

负责存储：

1. 会话
2. 消息
3. 会话记忆
4. 用户记忆
5. 执行级记忆
6. 任务
7. 任务步骤
8. Tool 执行记录
9. Workflow 运行记录
10. 运行日志

### 2.3 不跨库共表

约定：

1. 两个服务不共用业务表
2. `agent-core` 通过接口或缓存读取 `registry-center` 资源定义
3. `agent-core` 只保存运行时必要快照，不反向维护注册中心主数据

## 3. 通用建表规范

### 3.1 命名规范

1. 表名统一使用小写下划线 `snake_case`
2. 主键统一使用 `id`
3. 时间字段统一使用 `created_at`、`updated_at`
4. 创建人、更新人统一使用 `created_by`、`updated_by`
5. 逻辑删除字段统一使用 `is_deleted`
6. 状态字段统一使用 `status`
7. 备注字段统一使用 `remark`
8. 扩展信息统一使用 `metadata`

### 3.2 通用字段建议

除关系表外，核心业务表建议统一包含：

1. `id`
2. `status`
3. `remark`
4. `metadata`
5. `created_at`
6. `created_by`
7. `updated_at`
8. `updated_by`
9. `is_deleted`

### 3.3 主键建议

建议统一使用：

1. `bigint` 作为内部主键
2. 业务编码字段单独设计，例如 `agent_code`、`role_code`

说明：

1. 内部关联稳定用 `id`
2. 对外接口、配置引用优先用业务编码
3. `agent-core` 从 `registry-center` 拉取 Agent 可用 Tool / Workflow 时，应同步读取资源 `metadata`，用于运行时决策

### 3.4 状态字段原则

不要所有资源共用完全相同的状态语义。当前建议：

1. Agent：`draft`、`enabled`、`disabled`
2. Tool：`draft`、`enabled`、`disabled`
3. Workflow：`draft`、`published`、`disabled`
4. Prompt：`draft`、`enabled`、`disabled`
5. Role：`enabled`、`disabled`
6. Conversation：`pending`、`processing`、`success`、`failed`

运行时约定：

1. `registry-center` 的 Agent Tool 查询接口会透传 `tools.metadata`，并同时下发 Tool 对应的 Provider / Instance / Binding 信息
2. `agent-core` 决策阶段读取 `metadata.routing`、`input_schema`、`output_schema`、`providerType` 等摘要信息完成路由和参数规划
3. `agent-core` 执行阶段按 `providerType` 路由到 `internal / mcp / external_http` 适配器，不再只按 `toolCode -> 本地 Executor` 硬编码
4. 前端编辑页可用多行文本输入，但提交时建议转换为数组字段持久化；运行时允许兼容读取数组字段和 `...Text` 文本字段
5. 运行时优先评估 `metadata.policyCenter.rules`，未配置时继续兼容旧 `routing / guardrails / approval` 结构，不影响既有 Tool 决策链路
6. 当前已新增注册中心 `guardrail_policies` 策略中心，`agent-core` 会在构建 `ExecutionContext` 时拉取启用策略并注入到 Tool / Workflow 的 `policyCenter.rules`

## 12. Agent 异步运行队列

### 12.1 `agent_runs`

用途：

1. 持久化长任务入队状态，HTTP 请求无需等待 LLM 和 Tool 执行完成
2. 通过租约、心跳和 `SKIP LOCKED` 支持多 Worker 安全领取与故障接管
3. 通过 `idempotency_key`、`cancel_requested`、`task_id` 支持幂等、取消和执行链回查

核心字段：

| 字段名 | 类型建议 | 说明 |
| --- | --- | --- |
| run_code | varchar(64) | 异步运行编码，唯一 |
| conversation_id | bigint | 所属会话 ID |
| user_id | bigint | 发起用户 ID |
| agent_id | bigint | 执行 Agent ID，用于用户和 Agent 双维度公平调度 |
| input_text | text | 用户输入 |
| user_context | jsonb | 入队时固化的身份和权限上下文 |
| idempotency_key | varchar(128) | 客户端幂等键，同一会话和用户内唯一 |
| status | varchar(32) | `queued` / `running` / `completed` / `waiting_approval` / `waiting_event` / `paused` / `failed` / `cancelled` |
| attempt_count | integer | 已领取执行次数 |
| max_attempts | integer | 最大领取执行次数 |
| priority | integer | 持久化优先级，取值 0 到 100，并随等待时间 aging |
| available_at | timestamp | 下次允许领取时间 |
| lease_until | timestamp | Worker 租约截止时间 |
| heartbeat_at | timestamp | Worker 最近心跳时间 |
| worker_id | varchar(160) | 当前 Worker 实例标识 |
| task_id | bigint | 关联 `tasks.id` |
| cancel_requested | boolean | 是否请求取消 |
| error_message | varchar(1000) | 失败原因 |

补充规则：

1. `tasks.run_code` 与 `agent_runs.run_code` 一一对应，委派子任务不重复绑定 Run
2. Task 尚未创建时允许队列级重试；Task 已创建后只有存在安全 Checkpoint 且异常属于瞬时故障时才允许恢复，审批与取消不进入自动重试
3. Worker 必须持续续租；租约过期后其他实例可以重新领取
4. 领取使用 PostgreSQL advisory lock 与 `FOR UPDATE SKIP LOCKED`，在全局并发上限内按用户和 Agent 公平轮转
5. 总队列和单用户队列超过容量时拒绝入队，失败重试使用带稳定 jitter 的指数退避
6. 旧 Worker 租约失效后不得回写新 Worker 已接管的 Run，优雅停机期间必须续租并等待在途任务

### 12.2 `agent_run_stream_events`

用途：

1. 作为 Agent Run 的持久化 Runtime Event 首批事实源
2. 持久化 MiniMax、OpenAI-compatible 等模型供应商返回的原生 `delta.content`
3. 持久化不包含模型思维链的安全执行进度
4. 通过 `run_code + sequence_no` 支持多 Worker 实例下的有序消费和 SSE 断线续传
5. 使用 `message.reset` 标识新一轮最终回复生成，避免 Worker 重试后旧的部分输出与新输出拼接
6. 持久化 Run / Step 生命周期事件，支持前端状态驱动和后续 Simulation Replay
7. 持久化 Tool 调用生命周期；仅保存安全调用元数据，不保存参数值和原始输出正文
8. 持久化 Approval 生命周期，支持会话 UI 通过控制事件弹出、关闭审批窗口并在审批后续接原 Run
9. 持久化 Artifact 创建和发布生命周期，关联步骤产物事实、受保护下载地址和后续 Replay
10. 持久化 Checkpoint 创建和恢复生命周期，记录可重放边界及实际恢复入口，不复制快照正文
11. 持久化 Plan 创建和重规划生命周期，关联不可变计划版本、来源、质量评分和步骤差异摘要
12. 持久化 `policy.decided` Capability Policy 全量决策事实，供运营分页、聚合和 Tool Call 关联审计
13. 持久化图片输入路由和分析事实，只保存附件 ID、MIME、大小、SHA-256、路由和结果长度，不保存图片 Base64

核心字段：

| 字段名 | 类型建议 | 说明 |
| --- | --- | --- |
| id | bigint | 主键 |
| run_code | varchar(64) | 关联 `agent_runs.run_code`，Run 删除时级联清理 |
| sequence_no | bigint | Run 内单调递增序号，与 `run_code` 组成唯一约束 |
| event_type | varchar(64) | 可扩展 Runtime Event 类型；兼容历史 `reset / delta / progress` |
| content | text | 消息/进度事件正文；生命周期事件保存结构化 Payload JSON |
| metadata | jsonb | 安全执行阶段和事件扩展信息 |
| payload_version | smallint | Runtime Event Payload Schema 版本，当前为 `1` |
| created_at | timestamp | 事件创建时间 |

流式规则：

1. 只有会话 `metadata.interactionPolicy.responseStreamingEnabled=true` 且当前处于最终用户回复阶段时，才允许写入模型原生正文增量
2. Decision、Planner、Reflection、Judge 等内部 LLM 输出不得写入正文事件或发送给用户
3. 新写入事件使用标准编码；当前包含消息、进度以及 Run / Plan / Step / Tool / Approval / Artifact / Checkpoint 生命周期事件，读取时兼容历史 `reset / delta / progress`
4. 统一 SSE 通过 `/api/core/runtime/runs/{runCode}/events` 输出 `RuntimeEventEnvelope`，使用 `sequence_no` 作为 `Last-Event-ID`
5. 旧会话 SSE 继续将标准事件投影为 `reset / delta / progress`；任务完成后使用经过 Output Guardrails 且已落库的最终消息发送 `replace` 校准
6. `event_type` 只校验非空和最大长度，不使用数据库枚举约束阻断后续 Runtime Event 扩展
7. 不支持原生流式的 Provider 继续使用完整响应，前端保持普通轮询或最终内容分片兼容路径
8. Capability Policy 运营查询必须同时校验 `agent_runs.user_id / tenant_id / organization_id / workspace_id / project_id`，不得直接暴露 Event Repository
9. `idx_agent_run_stream_events_policy_audit(created_at DESC, run_code, id DESC)` 为 `event_type = 'policy.decided'` 的部分索引，用于全量决策按时间分页与 Run 关联；不改变 `run_code + sequence_no` 顺序约束

隔离与 Outbox 设计：

1. M1 复用 `agent_run_stream_events`，不重复新增 Event 表；`run_code + sequence_no` 唯一约束同时承担顺序约束和消费幂等键
2. 当前表不复制 `tenant_id / project_id / user_id`，统一 SSE 查询必须先通过 `AgentRunService` 按 `agent_runs.user_id` 校验 Run 归属，Repository 不直接暴露给 Controller
3. 若后续开放跨租户事件订阅，应在事件表冗余 `tenant_id / project_id`，增加 `(tenant_id, project_id, run_code, sequence_no)` 索引并启用与其他运行表一致的 PostgreSQL RLS；在此之前禁止提供绕过 Run 所有权校验的批量事件 API
4. M1 的本地 Runtime Event 是主运行事实，业务状态与关键事件尽量同事务直写，不经异步 Outbox 后才对当前 SSE 可见
5. 后续 `runtime_event_projection_outbox` 只服务外部 Projection / Webhook / Analytics，建议字段为 `id / event_id / projection_type / status / attempt_count / available_at / locked_by / locked_at / last_error / created_at / updated_at`
6. Outbox 使用 `event_id + projection_type` 唯一约束；状态为 `pending / processing / succeeded / failed`，通过 `FOR UPDATE SKIP LOCKED` 领取并按退避策略重试
7. Outbox 投影失败不得回滚已经发生的外部 Tool 副作用，也不得重新执行 Provider；只能重投同一不可变 Event

## 13. Knowledge 生产化存储

# 企业级作用域与隔离（2026-07-16）

## 租户层级

1. `tenants`：租户根边界，核心字段为 `tenant_code / tenant_name / status / metadata`。
2. `organizations`：租户内组织，通过 `tenant_id` 归属租户，租户内 `organization_code` 唯一。
3. `workspaces`：组织内资源工作区，通过 `tenant_id / organization_id` 保证父级归属。
4. `projects`：工作区内项目级隔离边界，通过 `tenant_id / organization_id / workspace_id` 形成完整层级。
5. `user_scope_memberships`：用户可切换作用域，保存 `user_id / tenant_id / organization_id / workspace_id / project_id / membership_role / is_default / status`。

`models / prompts / tools / workflows / agents / knowledge_bases / guardrail_policies` 已增加 `tenant_id / organization_id / workspace_id / project_id`。`agent-core` 的会话、任务、异步运行、记忆、Sandbox、Knowledge 审计和 Eval 数据也保存同一组作用域字段。

两个服务均在数据库连接借出时通过 `set_config` 注入 JWT 当前作用域，并对业务表启用 PostgreSQL `RLS + FORCE ROW LEVEL SECURITY`。策略规则为：普通请求只能访问当前 `tenant_id`；受控后台调度线程使用服务作用域读取待执行记录，领取后恢复记录内用户 JWT 作用域再继续执行。生产数据库连接必须使用非超级用户，否则 PostgreSQL 超级用户会绕过 RLS。

历史实例升级时自动创建 `DEFAULT / DEFAULT_ORG / DEFAULT_WORKSPACE / DEFAULT_PROJECT`，已有用户和资源迁移到默认项目，不破坏原有登录和数据。

### 17.3 `budget_policies`

用途：配置 `tenant / project / agent / user` 四级日预算或月预算。支持费用、LLM Token、Tool/MCP 次数、Sandbox 秒数、Delegation 次数五类限制，`warning_percent` 控制软阈值，`hard_limit=true` 时在资源调用前执行熔断。多个策略同时命中时全部生效，任一硬限制超限即拒绝调用。

### 17.4 `budget_alerts`

用途：保存 `warning / exceeded` 告警及 `open / acknowledged / resolved` 处理状态。同一策略、周期、指标和告警类型只保留一个打开告警，避免每次调用重复生成。

`usage_percent` 使用 `NUMERIC(18,2)`，避免长会话累计用量相对极小测试/试运行限额产生超大倍率时告警写入溢出，确保硬预算异常不会被上层降级路径吞掉。

以上四张表均启用 PostgreSQL `RLS + FORCE ROW LEVEL SECURITY`。运行时计量由 LLM 网关、Tool 路由、Sandbox 执行器和 Delegation 服务统一写入，业务 Tool 不允许自行维护另一套计费表。

## 18. Agent Run 分布式调度控制面

### 18.1 `agent_worker_groups`

保存 Worker Group 的 `group_code / max_concurrency / queue_capacity / required_capabilities / status`。`enabled` 接收入队和领取，`draining` 停止新流量但允许在途 Run 完成，`disabled` 完全停用。队列容量在入队事务内校验，组并发在 `SKIP LOCKED` 领取事务内校验。

### 18.2 `agent_worker_nodes`

保存项目作用域内的 Worker 注册、能力标签、最大并发、当前负载、启动时间和最近心跳。节点状态为 `online / draining / offline / unhealthy`；超过心跳阈值自动转为 `unhealthy`。`tenant_id + project_id + worker_id` 唯一，实际执行 Run 时按 Run 的 JWT 作用域补充心跳，因此控制面不会跨租户展示节点。

### 18.3 `agent_run_routing_rules`

按 `agent_id`、Run 优先级区间和规则顺序匹配目标 Worker Group，并将 `target_group_code / required_capabilities` 在入队时固化到 `agent_runs.worker_group_code / required_capabilities`。未命中规则时进入部署配置的默认组；目标组非 `enabled` 时不得路由。

Worker 仅领取本组且 `required_capabilities <@ worker.capabilities` 的 Run。原有用户/Agent 公平轮转、priority aging、lease、heartbeat、重试、取消、幂等和故障接管逻辑继续生效，控制面不替代数据面的一致性约束。

## 19. Prompt 实验与 Tool 输入契约治理

### 19.1 Prompt 实验

`registry-center` 使用 `prompt_versions / prompt_experiments / prompt_experiment_variants` 保存不可变 Prompt 内容版本、实验生命周期和带权 Variant。实验按 `user / conversation` 稳定哈希分流，支持 `system / decision / planner` 阶段、灰度比例、暂停、结束及胜出 Prompt 发布。

`agent-core` 使用 `prompt_experiment_exposures` 保存实际执行曝光，唯一约束 `task_id + stage` 防止重试重复计数，并关联 Task 状态、耗时和 `usage_events` 成本形成真实实验指标。运行时选择失败时回退基础 Prompt，不影响 Agent 主链可用性。

### 19.2 Tool 输入契约

`registry-center` 使用 `tool_input_contracts / tool_contract_test_cases` 保存 Tool Input Schema 版本、最大载荷、敏感路径、兼容性声明和发布前回归样例。Contract 至少存在一个回归用例且全部符合预期后才能发布，同一 Tool 原已发布版本自动进入 `deprecated`。

`agent-core` 使用 `tool_input_observations` 保存 Tool 调用的 Contract 版本、输入长度、内容哈希、Schema 结果、裁剪状态、错误分类和耗时。敏感输入不保存原文，仅保存脱敏路径和不可逆哈希。

以上八张表均保存 `tenant_id / organization_id / workspace_id / project_id`，对可独立查询的表启用 PostgreSQL `RLS + FORCE ROW LEVEL SECURITY`，禁止实验、契约和观测跨租户读取。

## 20. 外部 Tool / MCP 协议兼容性矩阵

`agent-core.tool_protocol_compatibility_runs` 保存每次实例级 Compatibility Suite 结果。核心字段为 `provider_type / transport_type / protocol_version / configuration_passed / connectivity_passed / discovery_passed / invocation_passed / failure_stage / checks / output_snapshot`。只有真实 invocation 成功才判定 `compatible`，并通过租户 RLS 隔离结果。

Registry 存量 Tool 初始化 Deployment 时，`deployment_code` 使用 `tool_code + instance_code + tool/instance hash` 的稳定组合，保证多个 Tool 共享同一个 Provider Instance 时仍全局唯一；每个 Tool 只选择一条确定性 Binding 生成基线 Deployment。

## 21. Tool 副作用幂等与补偿

`agent-core.tool_side_effect_executions` 记录有外部副作用的 Tool 调用。运行时在调用 Provider 前先以
`tenant_id + project_id + tool_code + idempotency_key` 原子占位，成功后保存结果快照；重复请求直接复用成功结果，
处于 `processing / uncertain` 的请求禁止自动重放，避免网络超时后重复写外部系统。

副作用权威等级由 Registry Tool 的 `side_effect_level` 保存；`metadata.sideEffectPolicy` 保存执行细节：

1. `level`：`none / idempotent / compensatable / irreversible`
2. `idempotencyMode`：`generated / required_custom`
3. `compensationToolCode`：`compensatable` 必填，任务最终失败时按副作用发生顺序逆序补偿

Registry 写入时强制 `side_effect_level` 与 `metadata.sideEffectPolicy.level` 一致。Core 新执行快照以顶层字段为权威，防止 metadata 被局部覆盖后降低副作用等级；仅对升级前历史快照回退读取旧 metadata。对于历史 MCP 快照中名称明确的写操作，Core 还会只提升、不降低其最低 Capability 和副作用等级，避免 `[] / none` 旧数据绕过审批。

表内保留原请求哈希、成功结果快照、错误、不确定状态及补偿状态，既用于运行时一致性控制，也形成独立审计链。

Checkpoint 恢复按 `tool_side_effect_executions.id` 逐条提交处置，禁止多条 `confirm_success` 共用同一个结果快照。`tool_side_effect_resolutions` 保存每次处置的原状态、动作、目标状态、结果快照、错误和操作人。`compensate` 动作会在重建原 Task `ExecutionContext` 后真实路由 `compensation_tool_code`；`confirm_compensated` 仅作为外部已完成补偿的兼容人工确认动作。

## 22. 持久化执行 Checkpoint

`agent-core.task_execution_checkpoints` 在每个 Plan Step 的 `started / succeeded / failed / waiting_approval`
边界保存原始 `ExecutionPlan`、`ExecutionDecision` 和已完成步骤结果。异步 Worker 租约失效后再次领取同一
`run_code` 时，优先复用原 Task、原用户消息和原计划，从最新安全边界继续执行，不重新创建消息或调用 Planner。

恢复语义为 at-least-once：发生进程级中断时，正在执行的步骤可能重放；有外部副作用的 Tool 必须同时配置
`sideEffectPolicy`，由 `tool_side_effect_executions` 的幂等键或补偿策略保证外部状态一致性。

Checkpoint 恢复会联查副作用执行状态。若步骤中断时存在 `processing/uncertain` 记录，则在
`task_execution_checkpoints.recovery_disposition` 标记 `manual_review` 并阻断自动重放；人工可确认成功、授权重试或确认已补偿，所有处置均记录解决人和解决时间。

每次 Checkpoint 快照插入与 `checkpoint.created` Runtime Event 位于同一事务。`checkpoint.restored` 仅在普通任务恢复或审批续跑实际加载快照时发布，并更新 `restored_at`；事件只保存 Checkpoint ID、步骤位置、Plan ID、恢复入口和安全处置，不复制 `plan_snapshot / decision_snapshot / step_results_snapshot` 正文。

`agent-core.task_plan_controls` 保存人工暂停、恢复、跳过步骤和单步执行请求。控制请求只在步骤边界消费，避免中断正在执行的 Tool；状态和消费时间构成独立审计链。

人工暂停使用正式的 `paused` 状态，并同步写入 `tasks / task_steps / agent_runs`。恢复动作先将暂停现场原子转换为现有 Recovery 可识别状态：异步任务重新进入持久化队列，同步任务立即调用标准恢复链。单步执行只允许当前待执行步骤，禁止为到达目标步骤而隐式执行中间步骤。

Checkpoint 分支通过独立 `task_id / task_code / trace_id / plan_id` 创建 `task_kind=checkpoint_fork` 子任务，`parent_task_id` 指向源任务，`root_task_id` 保留原任务树根节点。分支复制指定 Checkpoint 的不可变计划、决策和前序结果快照，不修改源任务及源 Trace。

步骤 `dataContract` 随 `task_plans / task_plan_steps` 的不可变版本快照保存。契约使用 `version / compatibleVersions` 描述生产者兼容范围，绑定使用 `sourceContractVersion` 在计划发布前校验版本，并通过 `sourcePointer / targetPointer` 支持嵌套 JSON Pointer 数据流。运行时递归校验对象、数组、字符串、数值、`enum/const/oneOf/anyOf/allOf` 等平台支持的 Schema 子集；未支持关键字明确阻断，不允许静默跳过。

结果可信度评估通过 `task_traces.metadata.resultTrust` 保存完整快照，包括 Claim 数量、证据覆盖、按 URI/文档去重后的独立来源、来源权威度、冲突 Claim 和 verifier 结果。`sourceStepId` 默认不计为独立外部来源；只有策略显式开启 `allowInternalStepEvidence` 时才参与来源计数。独立 verifier 支持单独 LLM 调用或指定 Tool，调用错误默认 fail-closed，可配置为只告警。

`agent-core.task_wait_subscriptions` 保存 timer/event/webhook 等待订阅。等待期间 `task/agent_run/task_step` 使用 `waiting_event` 状态并释放 Worker；到期或收到事件后 Run 重新入队并从持久化 Checkpoint 续跑。

同步执行首次进入等待时，如果 Task 尚未关联 `agent_runs`，运行时会自动创建 `waiting_event` Run，并将 `promoted_run_code` 写回订阅，保证进程重启或信号延迟到达后仍有持久化恢复载体。

外部 Webhook 使用 `/api/core/webhooks/waits/{eventKey}` 独立入口。签名原文为 `timestamp.nonce.eventKey.rawBody`，算法为 `HMAC-SHA256`；服务端校验时间窗口，并将 `(event_key, nonce)` 写入 `task_wait_webhook_nonces` 唯一约束，防止重放。生产环境必须通过 `CORE_WAIT_WEBHOOK_SECRET` 配置独立高强度密钥。

### 22.1 Interactive Loop 审批 Checkpoint

`agent-core.interactive_loop_checkpoints` 独立保存动态循环在 Capability 审批边界的恢复现场，不与强绑定
Plan/Step 的 `task_execution_checkpoints` 混用。核心字段如下：

1. `task_id + sequence_no`：同一 Task 内单调递增且唯一的快照序号
2. `checkpoint_status`：仅允许 `waiting_approval / restored`，恢复后不可重新打开
3. `budget_snapshot`：原始预算策略、累计用量以及仅含哈希的 Tool 重复指纹
4. `observations_snapshot`：审批前已完成并裁剪后的 Observation
5. `pending_action_snapshot`：触发审批且尚未完成的结构化 Tool Action
6. `approval_node_id / tool_call_id / parameter_hash`：审批恢复的强绑定键
7. `approval_metadata`：Capability Policy 产生的脱敏策略元数据
8. `trace_id / restored_at`：原执行 Trace 与实际恢复时间

表保存 `tenant_id / organization_id / workspace_id / project_id` 并启用 `RLS + FORCE ROW LEVEL SECURITY`。
恢复必须同时匹配 Task、Trace、审批节点、Tool Call ID 和参数哈希；恢复时只重放待审批 Tool，预算中的 Tool
调用次数不重复增加，历史 Observation 和重复指纹继续沿用。

## 23. Memory 与 Delegation 高阶治理

`agent-core.memory_governance_items` 将原有用户记忆汇总扩展为独立治理项，记录 `memory_type`、来源会话/消息/任务、
置信度、TTL、内容哈希、撤销原因以及 `supersedes / superseded_by` 双向替代关系。旧 `user_memories` 继续作为兼容汇总，
一旦用户产生治理项，上下文只读取未撤销且未过期的治理项；用户可通过 `/api/core/memories` 查询和撤销自己的记忆。

`task_delegations` 增加 `delegation_depth / required_capabilities / selection_reason / timeout_at /
cancellation_requested_at`。运行时根据 Agent `delegationPolicy` 控制最大深度、单任务扇出、超时和 Agent 回环，
支持 Planner 用 `requiredCapabilities` 自动选择目标 Agent，并在父异步 Run 取消时递归取消未完成子任务。

## 24. Agent Run 原生流与执行进度

`agent_runs.stream_event_sequence` 为每个 Run 原子分配单调递增游标，`agent_run_stream_events` 按
`run_code + sequence_no` 唯一保存可断线续传的 Runtime Event。当前标准 `event_type` 支持：

1. `run.progress`：安全执行阶段，包括上下文构建、决策、规划、Plan Step 和回复生成，不保存模型思维链。
2. `message.reset`：新的最终回复生成开始，前端清空尚未确认的正文。
3. `message.delta`：模型原生正文增量。
4. `run.queued / run.started / run.mode.selected / run.loop.stopped / run.waiting / run.completed / run.failed / run.cancelled`：Run 队列、执行模式选择、动态循环停止和终态变化；模式及循环事件只记录安全配置、计数和稳定原因，不记录 Prompt、Tool 参数或调用指纹。
5. `step.started / step.completed / step.failed / step.waiting`：Plan Step 生命周期；等待事件通过 Payload 中的 `status` 区分审批、外部事件和人工暂停。
6. `tool.call.requested / tool.call.started / tool.call.completed / tool.call.failed`：Tool 调用生命周期，使用 `toolCallId` 关联同一次调用；失败只保存错误分类，不保存供应商原始异常正文。
7. `approval.requested / approval.resolved / approval.revoked`：审批控制生命周期，使用 `approvalId` 关联审批；事件不保存审批意见和原始恢复元数据。
8. `artifact.created / artifact.published`：产物创建和发布生命周期，使用由 `taskId + path` 确定性生成的 `artifactId` 关联；事件不保存 `contentBase64` 文件正文。
9. `checkpoint.created / checkpoint.restored`：持久化执行边界和实际恢复生命周期，使用 `checkpointId` 关联；事件不复制 Plan、Decision 和 Step Results 快照正文。
10. `plan.created / plan.replanned`：计划创建和重规划生命周期，使用 `planId` 关联对应不可变计划版本；事件不复制目标、步骤、假设、约束和风险正文。
11. `input.attachment.resolved / input.attachment.analyzed`：冻结图片处理路由、附件引用、SHA-256 和分析结果长度；不得保存存储内部路径、图片 Base64 或外部 Provider 原始响应。

历史 `progress / reset / delta` 在查询时映射为对应标准类型。统一 SSE 使用固定事件名 `runtime.event`，
`data` 为版本化 `RuntimeEventEnvelope`；旧 SSE 继续兼容投影。消费端始终以数据库游标重放事件，不能依赖单机
内存事件总线。任务完成后旧接口以前端最终落库消息执行 `replace`，保证原生增量经过输出 Guardrails 后与持久化结果一致。
Run 终态/等待状态更新与对应事件写入必须位于同一数据库事务，避免 SSE 在终态关闭连接时遗漏最后事件。
人工审批、恢复或驳回后的 `agent_runs` 状态同步也必须追加同一事务内的新 `run.completed / run.failed / run.waiting`；相同状态和错误重复同步不得产生重复终态事件。
Tool Provider 调用前的事件写入失败时必须阻止调用；Provider 已返回后不得因结果事件写入失败自动重复执行，待后续 Event Projection Outbox 补齐可靠投影。
审批状态更新与对应事件写入位于同一事务；审批通过后的同步恢复必须重新绑定原 `run_code`，保证后续 Step / Tool 事件仍进入同一事件序列。
异步 Interactive Loop 在 LLM 和 Tool 边界同时读取 `agent_runs.cancel_requested`。取消命中后 Task 写入 `cancelled`，当前 Step 以 `failureType=cancelled` 结束，Run 写入 `cancelled` 并发布唯一 `run.cancelled`；取消后的下一次 LLM/Tool 调用不得启动。
产物生成事实来自成功 Step 的 `output_snapshot.payload.artifacts`；`artifact.created` 与步骤完成位于同一事务，`artifact.published` 只在最终回复确认受保护下载地址时写入，并与回复链接共用同一 URL 构建逻辑。
Checkpoint 快照插入与 `checkpoint.created` 位于同一事务；`checkpoint.restored` 在 `task_resume / approval_resume` 真正加载快照时写入，恢复前的安全性检查不提前产生恢复成功事件。
`task_plans / task_plan_steps` 版本快照与 Plan 事件位于同一事务；任务首版计划发布 `plan.created`，后续版本发布 `plan.replanned` 并携带上一版本标识及步骤增删改计数。
图片 Provider 调用前写入 `input.attachment.resolved`；调用成功后尽力写入 `input.attachment.analyzed`，后置事件失败不得重复调用 Provider。Simulation Replay 将两类事件作为录制事实注入并按规范 JSON 哈希比较，附件正文仍由附件存储和 `conversation_attachments.sha256` 管理。

## 25. Workflow 输出契约

Workflow 使用 `metadata.routing.outputMode` 声明其结果用途。值为 `user_reply` 时，表示 Workflow 内部已经完成
面向用户的回复生成；Planner 和 Plan Validator 不得再自动追加同义 `reply` 或最终 LLM 汇总。确需基于 Workflow
结果二次改写时，显式在尾部 `reply.inputs.forceResponseRewrite=true`，由配置覆盖默认去重策略。

Workflow 详情快照必须携带 `metadata`。运行时组装 `user_reply` 输出时直接使用末次回复节点的完整
`responseText`，不得转换为“已执行 Workflow”调试摘要，也不得按观测摘要长度截断用户正文。

## 26. Runtime Replay 审计实例

`agent-core.runtime_replays` 保存独立 Replay 实例，正式区分 `prompt_replay / simulation_replay / execution_replay`。M2 首个切片只开放 `prompt_replay`；后两种先冻结契约，`execution_replay` 不开放生产入口。

核心字段：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `replay_code` | varchar(64) | Replay 唯一编码 |
| `replay_trace_id` | varchar(64) | Replay 独立 Trace ID，不复用来源 Trace |
| `replay_mode` | varchar(32) | 三种 Replay Mode |
| `source_run_code` | varchar(64) | 原 Run 编码，可为空 |
| `source_task_id` | bigint | 原 Task ID，外键关联但不回写 |
| `source_task_trace_id` | bigint | 原 Task Trace ID |
| `user_id` | bigint | 发起管理员 |
| `status` | varchar(24) | `pending / running / succeeded / failed` |
| `manifest` | jsonb | 模型、Prompt、资源可用性、Policy、执行模式摘要 |
| `input_snapshot` | jsonb | 创建前冻结的 Replay Input |
| `result_snapshot` | jsonb | Replay 独立输出、指标和 Diff |
| `error_message` | varchar(1000) | 失败原因 |

约束：

1. `manifest / input_snapshot` 只在 INSERT 时写入，完成或失败更新不得覆盖
2. Prompt Replay Manifest 不保存模型密钥、基础地址、Tool 认证和请求头
3. Prompt Replay 固定禁止 Tool、Workflow、网络写、文件写和数据库业务写
4. Replay 使用独立 `replay_trace_id` 写入观测 Span，原 Trace 行保持不可变
5. 来源快照不完整时明确失败；`eventRange.available=false` 表示没有 Run Event 游标，不能填充伪造范围
6. Simulation Replay Input 同时冻结 `agent_run_stream_events` 事件范围和 `task_steps.output_snapshot` 录制结果；事件序号必须连续
7. `step.completed` 必须关联成功步骤的有效 JSON 快照和 `resultType`，缺失时 Replay 失败，不从当前 Tool Provider 补取
8. 录制步骤结果保存原快照 SHA-256，用于证明注入来源；本阶段不修改原步骤快照
9. Simulation Replay 允许写 `runtime_replays` 和独立 Replay Trace 审计数据，但禁止写业务 Task、Step、Approval、Artifact 和外部系统
10. Simulation Replay 完成后将结构化 `eventDiff` 写入 `result_snapshot.eventDiff`，不新增可变 Diff 表
11. Diff 事实使用稳定键对齐并保存规范 JSON 哈希；`matched / changed / missing / unexpected` 只描述 Replay 结果，不反向修改来源事件
12. `result_snapshot.eventDiff.resultDiff` 保存来源消息投影与 Replay 重组消息及其 SHA-256，便于审计结果组装一致性
13. Simulation Replay 从 `input_snapshot.recordedStepResults[*].outputSnapshot.payload.artifacts.contentBase64` 读取冻结内容，不读取已清理的 Sandbox Workspace
14. `input_snapshot.recordedArtifacts` 只保存 Artifact ID、路径、声明/实际大小、媒体类型和内容 SHA-256，不重复保存 Base64 正文
15. `result_snapshot.artifactVerification` 保存内容与 `artifact.created / artifact.published` 元数据校验报告；报告不修改来源 Artifact
16. Artifact 内容缺失、损坏或路径不安全时 Replay 明确失败；可验证内容与声明/事件元数据不一致时保存 `metadata_mismatch` 供审计
17. `runtime_replays.manifest.featureDecision` 保存本次 Replay 的模式、灰度原因和稳定分桶，不保存完整白名单配置
18. Replay Feature Flag 只控制新执行入口，不改变 `runtime_replays` 表结构，不删除或覆盖历史 Manifest/Input/Result
19. 未命中灰度的请求在 Replay 实例创建前失败，因此不得产生空的 `runtime_replays` 记录

## 27. Runtime Plugin Registry 治理

`registry-center` 负责 Runtime Plugin 的定义、版本、安装和 Agent 绑定；`agent-core` 仍只负责加载和执行。两个服务不直连对方数据库。

### 27.1 `runtime_plugins`

用途：保存项目作用域内稳定的插件身份。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `plugin_code` | varchar(64) | Manifest 稳定编码，`tenant_id + project_id` 内唯一 |
| `plugin_name` | varchar(128) | 插件展示名称 |
| `description` | varchar(1000) | 插件用途说明 |
| `status` | varchar(32) | `enabled / disabled` |
| `metadata` | jsonb | 非敏感扩展信息 |
| `tenant_id / organization_id / workspace_id / project_id` | bigint | 企业作用域 |
| `created_at / created_by / updated_at / updated_by` | timestamp / bigint | 创建和更新审计 |
| `is_deleted` | boolean | 逻辑删除标记 |

### 27.2 `runtime_plugin_versions`

用途：保存不可变 Manifest 和 Jar 制品完整性信息。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `plugin_id` | bigint | 所属插件定义 |
| `version` | varchar(64) | 严格 SemVer，同一插件内唯一 |
| `platform_api_version` | varchar(16) | 目标平台 API 主版本 |
| `entrypoint` | varchar(255) | `AgentRuntimePlugin` Provider 全限定类名 |
| `manifest` | jsonb | 完整不可变 Manifest 快照 |
| `artifact_uri` | varchar(500) | Jar 制品地址 |
| `artifact_sha256` | char(64) | Jar SHA-256 |
| `release_notes` | varchar(1000) | 发布说明 |
| `status` | varchar(32) | `draft / published / deprecated` |
| `published_at` | timestamp | 首次发布时间 |

Manifest、入口类、制品 URI 和 SHA-256 不提供更新接口，只允许 `draft -> published -> deprecated`，废弃版本可重新发布。存在已启用安装时不允许废弃。

### 27.3 `runtime_plugin_installations`

用途：保存指定环境的当前安装版本和加载期望。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `plugin_id / version_id` | bigint | 插件和当前版本 |
| `environment_code` | varchar(64) | 环境编码，同一插件环境唯一 |
| `status` | varchar(32) | 期望状态：`enabled / disabled / uninstalled` |
| `load_status` | varchar(32) | 加载状态：`pending_restart / loaded / failed / not_loaded` |
| `observed_plugin_code` | varchar(64) | Core 最近实际发现的插件编码 |
| `observed_version` | varchar(64) | Core 最近实际加载的插件版本 |
| `observed_artifact_sha256` | char(64) | 可计算时的实际 Jar SHA-256 |
| `last_error` | varchar(1000) | 最近加载错误 |
| `metadata` | jsonb | 非敏感安装元数据 |
| `installed_at / enabled_at / disabled_at / uninstalled_at` | timestamp | 安装生命周期时间 |
| `loaded_at` | timestamp | 最近一次确认加载成功时间 |
| `last_reported_at` | timestamp | Core 最近回写加载结果时间 |

当前不支持 JVM 热替换，安装、替换、启停和卸载均先写入 `pending_restart`。Core 按环境读取已启用、已发布的期望安装，核对实际插件编码、版本和可计算的制品摘要后回写 `loaded / failed / not_loaded`，Registry 不伪造已生效状态。每次回写同步更新 `last_reported_at` 并写入生命周期审计；失败保存稳定错误码与安全摘要，不保存堆栈、Token、Tool 参数或 Prompt。

Core 使用跨租户服务身份回写时，加载审计必须从 `runtime_plugin_installations` 显式继承 `tenant_id / organization_id / workspace_id / project_id`，不能依赖服务线程的默认数据库作用域，避免审计写入默认租户后对插件所属项目不可见。

### 27.4 `agent_runtime_plugin_rel`

用途：将 Agent 绑定到唯一的具体环境安装。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `agent_id` | bigint | Agent ID |
| `plugin_id` | bigint | Runtime Plugin ID |
| `installation_id` | bigint | 具体环境安装 ID |
| `required` | boolean | 插件不可用时是否阻断 Agent 运行 |
| `tenant_id / organization_id / workspace_id / project_id` | bigint | 企业作用域 |
| `created_at / created_by / updated_at / updated_by` | timestamp / bigint | 绑定审计 |
| `is_deleted` | boolean | 逻辑删除标记 |

同一 Agent 对同一插件最多一个有效绑定。只允许绑定定义已启用、版本已发布、安装已启用的记录；安装替换版本、停用或卸载前必须先解除绑定。

### 27.5 `runtime_plugin_lifecycle_audits`

用途：记录插件定义、版本、安装、状态与 Agent 绑定变更。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `plugin_id / version_id / installation_id / agent_id` | bigint | 变更关联资源 |
| `action` | varchar(64) | `create_plugin / create_version / install / bind_agent` 等动作 |
| `before_state / after_state` | jsonb | 不含密钥、Tool 参数或 Prompt 正文的安全快照 |
| `result` | varchar(32) | `success / failed` |
| `message` | varchar(1000) | 操作摘要 |
| `operator_id / created_at` | bigint / timestamp | 操作人和时间 |

五张新表都包含企业作用域字段并开启 PostgreSQL RLS。插件关系同时通过复合外键保证版本和安装归属同一插件。

## 28. 会话多模态附件

### 28.1 `conversation_attachments`

用途：保存会话输入、输出附件的运行时元数据。文件正文保存于本地存储、MinIO、S3 或兼容对象存储，不写入 PostgreSQL。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attachment_code` | varchar(64) | 稳定附件编码，全局唯一 |
| `conversation_id` | bigint | 所属会话，必须引用 `conversations.id` |
| `message_id` | bigint | 关联消息；先上传后发送消息时允许暂时为空 |
| `run_code` | varchar(64) | 关联异步 Run 编码，可为空 |
| `direction` | varchar(16) | `input / output` |

| `mime_type` | varchar(128) | 根据文件签名识别的 MIME，不信任客户端声明 |
| `size_bytes` | bigint | 文件正文大小，必须大于 0 |
| `sha256` | char(64) | 文件正文 SHA-256，用于下载和 Replay 完整性校验 |
| `storage_provider` | varchar(32) | `local / minio / s3` 等存储实现编码 |
| `storage_key` | varchar(500) | 存储内部键，不作为公开 URL |

| `is_deleted` | boolean | 逻辑删除标记 |

约束：

1. 上传接口先校验会话归属，再校验文件大小和真实签名
2. 当前首期只允许 `image/jpeg`、`image/png`、`image/webp`，默认单文件最大 10 MB
3. `storage_provider + storage_key` 唯一，附件响应不得暴露 `storage_key`
4. 表启用 PostgreSQL RLS，并按 `tenant_id / project_id` 建立作用域索引
5. 下载同时校验会话用户归属和内容 SHA-256，避免跨会话读取或静默损坏
6. 后续消息绑定、异步 Run 和 Replay 只保存附件引用，不复制 Base64 正文
7. 异步消息入队时先以 `run_code` 原子预留附件，Worker 创建用户消息后再写入 `message_id`
8. 已绑定 `message_id` 或 `run_code` 的附件禁止删除，未发送附件允许逻辑删除并清理存储正文

### 28.2 图片理解 Tool 注册

`registry-center` 通过迁移注册 `IMAGE_OCR` 与 `IMAGE_LAYOUT_ANALYZE`，复用平台内置进程内 Provider、版本和部署模型，不新增业务表：

1. 两个 Tool 的 `tool_type=image`、`tool_category=multimodal`，均声明 `filesystem.read` 和 `side_effect_level=none`
2. 输入只允许 `attachmentId` 及识别控制参数，不接受或持久化 `contentBase64`
3. Tool 执行时只能从当前 `ExecutionContext.messageContext.attachments` 选择附件，再由附件服务校验会话、绑定状态、存储 Provider 与 SHA-256
4. 输出快照只保存附件引用、SHA-256、版面元数据或 OCR 文本；图片二进制正文始终留在附件存储
