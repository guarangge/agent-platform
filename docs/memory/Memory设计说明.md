# Memory 设计说明

## 1. 结论

本项目当前的 `Memory` 设计，目标不是保存全部原始会话，而是把可复用的信息按层次沉淀为结构化记忆，供后续执行链路读取和注入。

当前记忆分为三层：

1. 会话级记忆
2. 用户级记忆
3. 执行级记忆

当前实现特点：

1. 原始消息、任务、步骤照常完整保存
2. `Memory` 保存的是处理后的摘要或结构化结果，不是原文回放
3. 当前提取方式以规则为主，不调用 `LLM`
4. 后期建议升级为：规则提候选 + `LLM` 归一化/压缩 + 规则合并保存

---

## 2. 设计目标

`Memory` 主要解决四类问题：

1. 当前会话最近在聊什么
2. 当前用户长期偏好什么、关注什么、目标什么
3. 某一次任务执行得出了什么关键结果
4. 执行下一轮时，哪些历史信息值得被重新注入

`Memory` 与 `Context` 的边界：

1. `ExecutionContext` 是本次执行现场
2. `Memory` 是执行后沉淀下来、可跨轮次复用的信息

---

## 3. 分类设计

### 3.1 会话级记忆

用途：

1. 记录当前会话最近在聊什么
2. 支撑同一会话内的多轮连续对话

当前字段：

1. `memorySummary`
2. `preferenceSummary`
3. `lastUserMessage`
4. `lastAssistantSummary`

说明：

1. 会话级记忆偏最近态
2. 更适合覆盖更新，不强调长期累计

---

### 3.2 用户级记忆

用途：

1. 记录跨会话稳定偏好
2. 记录长期关注主题
3. 记录相对稳定事实和长期目标

当前字段：

1. `preferenceSummary`
2. `attentionSummary`
3. `factSummary`
4. `goalSummary`

说明：

1. 用户级记忆偏长期
2. 更新方式以增量合并为主

---

### 3.3 执行级记忆

用途：

1. 记录某一次 `task` 的关键结果
2. 支撑续问、恢复和最近任务回放

当前字段：

1. `memorySummary`
2. `keyFindings`
3. `finalResponseSummary`

说明：

1. 执行级记忆按任务新增
2. 不覆盖其他任务历史

---

## 4. 数据来源

### 4.1 原始来源

所有 `Memory` 的基础来源都是以下原始数据：

1. 本轮 `userMessage`
2. 本轮 `assistantContent`
3. 本轮 `task` 执行结果
4. 本轮 `task_step` 输入/输出快照
5. 既有会话级记忆
6. 既有用户级记忆

### 4.2 原始数据与记忆的关系

当前不是直接把原始会话当作记忆保存，而是：

```text
原始消息 / 原始任务 / 原始步骤
-> 规则提取
-> 结构化摘要
-> 保存为 Memory
```

所以：

1. `messages` 保存原文
2. `tasks / task_steps` 保存执行现场
3. `Memory` 保存提炼结果

---

## 5. 当前字段含义

### 5.1 会话级字段

#### `memorySummary`

含义：

1. 当前会话最近在聊什么
2. 最近用户问题是什么
3. 最近助手回复摘要是什么

当前实现：

1. 基于 `agentName + userMessage + assistantContent`
2. 使用固定模板拼接摘要

#### `preferenceSummary`

含义：

1. 当前这条会话里表现出的短期关注方向

当前实现：

1. 按关键词判断当前轮更偏高考、专业、文档设计、时间信息等主题

#### `lastUserMessage`

含义：

1. 最近一次用户问题

当前实现：

1. 保存本轮用户输入截断文本

#### `lastAssistantSummary`

含义：

1. 最近一次助手回复摘要

当前实现：

1. 保存本轮助手输出截断文本

---

### 5.2 用户级字段

#### `preferenceSummary`

含义：

1. 用户长期风格偏好
2. 用户长期领域偏好

示例：

1. `偏好简洁回答`
2. `偏好计算机相关方向`

#### `attentionSummary`

含义：

1. 用户长期关注的主题

示例：

1. `长期关注高考志愿分析`
2. `长期关注平台文档与架构说明`

#### `factSummary`

含义：

1. 用户稳定事实

示例：

1. `用户曾提到分数约为612分`
2. `用户偏向计算机相关专业`

#### `goalSummary`

含义：

1. 用户长期目标

示例：

1. `希望获得志愿填报建议`
2. `希望获取平台文档与设计说明`

---

### 5.3 执行级字段

#### `memorySummary`

含义：

1. 本次任务做了什么

#### `keyFindings`

含义：

1. 本次任务的关键发现

#### `finalResponseSummary`

含义：

1. 本次任务最后给出的结论

---

## 6. 当前规则提取逻辑

当前规则主要位于：

1. `MemoryUpdaterService`

当前是：

1. 关键词规则
2. 模板拼接
3. 去重合并

不是：

1. `LLM` 总结
2. 全量会话重写

### 6.1 会话级规则

#### `memorySummary`

当前模板大意：

```text
当前会话围绕「Agent」进行，最近用户问题为「...」，最近响应摘要为「...」。
```

#### `preferenceSummary`

当前关键词：

1. `高考 / 分数 / 志愿` -> `关注高考志愿分析`
2. `专业` -> `关注专业方向`
3. `文档 / 数据库 / 接口 / 设计` -> `关注平台文档与设计说明`
4. `时间 / 日期 / 时区` -> `关注时间信息`

---

### 6.2 用户级规则

#### `preferenceSummary`

当前关键词：

1. `计算机` -> `偏好计算机相关方向`
2. `简洁` -> `偏好简洁回答`
3. `专业` -> `会持续关注专业选择`

#### `attentionSummary`

当前关键词：

1. `高考 / 分数 / 志愿` -> `长期关注高考志愿分析`
2. `文档 / 数据库 / 接口 / 设计` -> `长期关注平台文档与架构说明`
3. `时间 / 日期 / 时区` -> `会查询时间与时区信息`

#### `factSummary`

当前关键词：

1. `高考` -> `用户参加高考相关咨询`
2. 命中三位分数模式或示例分数 -> `用户曾提到分数约为612分`
3. `计算机` -> `用户偏向计算机相关专业`

#### `goalSummary`

当前关键词：

1. `志愿` -> `希望获得志愿填报建议`
2. `专业` -> `希望明确合适的专业方向`
3. `文档 / 设计 / 数据库` -> `希望获取平台文档与设计说明`

---

## 7. 更新触发逻辑

当前不是“先判断要不要触发再更新”，而是：

1. 本轮执行成功
2. 固定进入 `MemoryUpdaterService`
3. 内部按规则更新对应记忆

当前通常在这些场景更新：

1. 正常问答执行成功
2. 审批继续执行成功
3. 恢复执行成功

当前通常这些场景不更新：

1. 执行失败
2. 审批挂起未完成
3. 审批拒绝直接结束

---

## 8. 覆盖、合并与去重逻辑

### 8.1 会话级记忆

当前更偏覆盖最近态：

1. `lastUserMessage` 直接更新为最新问题
2. `lastAssistantSummary` 直接更新为最新回复摘要
3. `memorySummary` 重新生成最新摘要
4. `preferenceSummary` 重新按当前轮消息提取

### 8.2 用户级记忆

当前更偏增量合并：

1. 先读旧值
2. 从本轮消息提取新条目
3. 去重合并
4. 再写回

### 8.3 执行级记忆

当前按任务新增：

1. 每个 `task` 生成自己的执行级记忆快照

### 8.4 当前去重方式

当前主要是：

1. 按 `；` 拆分条目
2. 去空白
3. 完全相同项去重
4. 重新拼接

也就是说：

1. 规则层擅长处理“完全一致去重”
2. 还不处理“语义相近归并”

---

## 9. 后期推荐演进路径

后期不建议走“每轮把所有旧记忆 + 最新问答都交给 LLM 全量重写”。

更合理的路径是：

```text
执行前读取记忆
-> 规则选择候选记忆
-> 必要时由 LLM 精筛 / 压缩
-> 执行
-> 执行后提取增量记忆
-> 与旧记忆合并
-> 达到阈值时做压缩
```

### 9.1 推荐分层

1. `MemoryCandidateExtractor`
2. `MemoryRuleDeduplicator`
3. `LlmMemoryNormalizer`
4. `MemoryMergeService`
5. `MemoryPersistService`

### 9.2 LLM 适合做什么

1. 候选记忆语义归一化
2. 同义表达合并
3. 长记忆压缩
4. 更自然的摘要润色

### 9.3 不建议 LLM 直接做什么

1. 不建议直接替代原始消息和任务记录
2. 不建议直接全量重写数据库里的旧记忆
3. 不建议直接决定最终保存格式

---

## 10. 推荐的后期实现流程

推荐完整流程：

```text
旧记忆 + 新候选记忆
-> 规则层完全一致去重
-> LLM 做语义归一化
-> 规则层再次去重
-> 合并保存
```

这个流程的目的：

1. 保持结构稳定
2. 保持结果可控
3. 减少 LLM 漂移
4. 兼顾语义能力和工程可维护性

---

## 11. 当前阶段结论

当前阶段最合理的策略是：

1. 继续用规则维护基础记忆结构
2. 先把字段边界和更新逻辑稳定下来
3. 后续再引入 `LLM` 做候选记忆归一化与压缩
4. 不要在当前阶段让 `LLM` 直接主导所有记忆保存逻辑

一句话总结：

**当前 `Memory` 是“规则提取 + 规则合并 + 摘要保存”，后期建议升级成“规则提候选 + LLM 归一化 + 规则保存”。**
